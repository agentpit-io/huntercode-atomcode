## 0. 一页结论

1. **底座集成跑通了**：daemon 起在 compose 内网、`GET /skills` 列出全部 **6 个技能**、
   `GET /mcp/status` **9/9 connected（28 个工具）**、hook 真的被加载并逐条记账、
   `deploy/up.sh` 一条命令可重复拉起（本轮从零拉起 4 次）。
2. **6 个技能全部被真实模型认出来并执行**（`use_skill` 事件 6/6，技能正文确实被注入），
   MCP 工具被真实调用 **25 次**，其中 **15 次拿回真数据**（比亚迪龙虎榜席位、
   AKShare 函数检索与签名等，见 §7）。
3. **但 6 个 hunter 系 MCP 在 M1 的部署里调不通** —— 它们是反调 HunterCode 后端的薄代理，
   而 M1 按任务书只起 daemon + llm-shim、**没有 api 服务**，调用一律
   `ConnectError: Temporary failure in name resolution`。技能里最值钱的
   `uzi_stock_deep_analysis` 因此拿不到数据。这是**已知的范围内缺口**，不是 bug，
   但必须说清楚：**M1 证明的是"挂得上、调得动"，不是"数据全通"**（待办池 P0-8）。
4. **本轮最重要的新发现：`POST /live/switch_session` 之后 MCP 工具会全部消失，
   而 `/mcp/status` 仍然显示 9/9 connected。** 受控实验见 §7.3。
   这直接决定 M2 的 Web 转发层怎么写 —— 用户点一下"历史对话"就会悄悄失去全部数据源。
   已验证的绕法：切完会话后 `POST /mcp/reload` **并等到不再有 `connecting`**。
5. 另外三个踩过的坑，都已在代码里修掉并留了注释：
   `.hooks.json` 不许写注释且解析失败是静默的（§5.2）、
   6 个 hunter 系 MCP 与 `mcp` 2.x 不兼容（§3.2）、
   9 个 MCP 同时冷启动在 2 核机器上会超时（§6.3）。
6. **M0 的 P0-7 在本轮复现了 3 次**：模型宣告"正在查询 X"然后不发工具调用，
   流以 `stop_reason=stopped` 正常收尾，任务只做了一半（§7.2）。
   这是 M2 转发层必须自己兜的。

**本轮没做的**：`/chat` 通道的技能验证（`/chat` 不挂 MCP，做了也是空的，§7.1 说明为什么改走 `/live`）、
web/api 接入（M2）、llm-shim 端到端收益复测（P0-6，本轮额度不够，§9）。

## 2. daemon 镜像（Dockerfile.daemon）

### 2.1 二进制校验：两道都过

第 1 段 `atomcode-fetch` 从 npm 取 `@atomgit.com/atomcode@5.1.0-linux-x64`，
**tgz 与解包出的二进制各校验一次 sha256**，值来自 `pins.lock`（M0 实测）：

```
+ npm pack @atomgit.com/atomcode@5.1.0-linux-x64
+ echo 220ea8d7b31c4482b7235fa251d266be080f8fedbf6d89d44f4cf642bfc872f5  ./atomgit.com-atomcode-5.1.0-linux-x64.tgz | sha256sum -c -
+ tar xzf … package/bin/atomcode
+ echo 40d86fa3e31980dbcdc8a6e5707c822f3953284ff76b31523789ca19988c8763  package/bin/atomcode | sha256sum -c -
+ /out/atomcode --version
atomcode 5.1.0 (unknown)
```

`sha256sum -c` 不过就是非零退出，整个构建当场失败，**没有"跳过校验"的开关**。
运行时还有一道旁证：`GET /health` 回显的 `binary_hash` 与 `pins.lock` 逐字相同（§6.1）。

### 2.2 非 root

固定 `uid/gid = 10001`（便于宿主给数据卷对权限），`USER hca`，
`security_opt: no-new-privileges`。`/data`、`/workspace`、`/run/hca` 在镜像里先建好并
`chown` —— Docker 给新建的具名卷默认 `root:root`，不先占上属主的话非 root 进程写不进去。

### 2.3 健康检查

`HEALTHCHECK` 打 `http://127.0.0.1:${HCA_DAEMON_PORT}/health`，也就是 **socat 那一层**
而不是 daemon 的回环端口 —— 这样一次检查同时覆盖 daemon 与转发，
不会漏掉"daemon 活着但容器网络上连不上"。`start-period` 给 120 秒（9 个 MCP 要冷启动）。

### 3.2 ⚠️ 踩坑：6 个 hunter 系 MCP 和 `mcp` 2.x 不兼容

第一次构建把 9 个 MCP 放进同一个 venv（`mcp>=2.0.0`），结果 `/mcp/status` 是
**3/9 connected**，失败的 6 个统一报 `MCP server closed stdout` —— 这句话什么也没告诉你。
用 `dump_mcp_tools.py` 直连才看到真正的报错：

```
uzi  ✗ 失败   原因：RuntimeError: server 提前退出（exit=1）：
  File "/opt/hca/mcp/uzi_mcp.py", line 63, in <module>
    @server.list_tools()
AttributeError: 'Server' object has no attribute 'list_tools'
```

根因：`mcp` 2.x 把 FastMCP 改名 MCPServer 的同时，**去掉了 1.x 的
`@server.list_tools()` 装饰器**。`mcp.server.Server` 这个类在 2.x 里**还在、还能 import**，
所以构建期那条只验 import 的自检**一路绿灯放行**。

**修法**：镜像里开两个 venv，各自干净。

| venv | mcp 版本 | 服务 |
|---|---|---|
| `/opt/hca/venv` | 2.x | akshare / kronos / truesource（用 `MCPServer` 新 API） |
| `/opt/hca/venv-hunter` | `>=1.30,<2` | uzi / watchlist / portfolio / screener / hunter_cap / hunter_user |

同时把构建期自检从"import 得到吗"改成"**实例化 `Server` 并检查装饰器在不在**"：

```
venv 自检：akshare 1.18.97
venv-hunter 自检：Server 装饰器 API 在
```

把这 6 个脚本升到 mcp 2.x 属于改从 hunter-community 导入来的业务代码，不在 M1 范围，
记进待办池 P1-13。

### 3.3 密钥不落盘：`${VAR}` 交给 AtomCode 自己展开

`.mcp.json` 里写的是 `${HERMES_API_URL:-http://api:8000}` 这种占位，**原样铺进工作区、我们不预渲染**。
AtomCode 自己会展开（上游 `mcp/config.rs:315-336`，`command` / `args` / `env` 三处都走
`expand_env_vars`，支持的正是 `${VAR}` 与 `${VAR:-默认值}`，`config.rs:797+` 有单测）。

这么做的好处是 **`KRONOS_API_KEY` / `HUNTER_API_KEY` / `HUNTER_INTERNAL_KEY` 不会以明文
落进工作区数据卷**，只活在 daemon 进程的环境里。

实测确实生效（不然这 6 个 MCP 会拿着字面量 `${HERMES_API_URL:-…}` 当 URL）：

```json
{"error": "hermes-api call failed: ConnectError: …", "hermes_api": "http://api:8000", "tool": "stock_news"}
```

另外 `AKSHARE_MAX_ROWS=50` 也实测生效 —— 比亚迪龙虎榜那次返回 `"rows": 50, "total": 53`，
正好被截在 50。

### 3.4 `autoApprove` 预置

M0 §5.7 实测 MCP 工具默认**每次调用都弹权限**。模板里 9 个 server 的 28 个工具全部预置进
`autoApprove`（收的是不带 `mcp__` 前缀的原名）。
本轮 6 个用例 **25 次 MCP 调用，0 次权限弹窗**，预置有效。
`tools/tests/test_build_skills.py` 里有一条单测专门比对 `autoApprove` 与 `mcp-tools.json`
不许漂。

### 4.2 三处偏离任务书的做法，以及为什么

**① `{股票}` 没有无脑换成 `$ARGUMENTS`。** 先把仓库里 `{…}` 的实际分布数清楚了：

| 出现位置 | 例子 | 是什么 | 处理 |
|---|---|---|---|
| `hunter.prompt_tpl`（5 个技能） | `帮我写一份 {股票} 的深度投研报告` | **前端**预填输入框用的模板 | **原样保留** —— 换掉前端提示语就变成"帮我写一份 $ARGUMENTS 的…" |
| `references/*.md`（investor_panel，30 处） | `{真实数字}` | 给模型的**输出**填空指引 | **原样保留** —— 换掉会把 9 份打分细则全写坏 |
| SKILL.md 正文 | 目前 0 处 | 真正的入参占位 | 换成 `$ARGUMENTS`（规则已实现并有单测） |

真正要解决的是"参数怎么进正文"，做法是在正文末尾生成一段 `## 参数` 区块显式写上
`$ARGUMENTS`，占位符名字从 `prompt_tpl` 推出来：

```markdown
<!-- HCA:BEGIN 由 tools/build_skills.py 生成，勿手改 -->

## 参数

本技能的入参是**股票**（代码或名称都可以）。用户这次给的是：

$ARGUMENTS

参数为空时，先问清楚要看哪只标的再开工，**不要随便挑一只演示**。

## 工具名对照

| 正文里的写法 | 实际要调的工具 |
|---|---|
| `uzi_stock_deep_analysis` | `mcp__uzi__stock_deep_analysis` |
…
<!-- HCA:END -->
```

（补充事实：上游 `skills/skill.rs::expand` 在模板**没有** `$ARGUMENTS` 时会把参数
**追加**到末尾，所以显式写不是必须的，但能控制参数出现的位置和措辞。）

**② 正文里的工具名也改了。** 只改 `allowed-tools` 救不了实际调用 ——
SKILL 正文是写给模型看的操作说明，里面直接点名「调用 `uzi_stock_deep_analysis`」，
而 AtomCode 下这个名字不存在。M0 §11.1 用例 6 实测过后果：模型老老实实去找
`portfolio_update_risk_profile`，找不到，只好改口说明情况。
转换器把**反引号里、且是 `<服务>_<工具>` 完整形式**的出现替换成真名
（裸工具名如 `invoke` / `market_screen` 不碰，中文正文里太容易误伤）。

**③ `hunter:` 扩展字段原样保留**（M0 §6 已证明不会导致解析失败）。
前端要的 `display_name` / `icon` / `category` / `prompt_tpl` 只能从 SKILL.md 自己读，
`GET /skills` 拿不到（待办池 P1-3）。

### 4.3 ⚠️ 必须说清楚：`allowed-tools` 在 5.1.0 里**不生效**

上游 `skills/skill.rs:260` 解析了它、存进 `Skill.allowed_tools`，字段注释自己写着
"the L1 capability does not enforce it — that's an L2 approval-policy concern"，
而**全仓库 grep `.allowed_tools` 只有定义处与构造处，没有读取方**；`GET /skills` 也不回它。

所以这个字段目前是纯元数据：写了不限制模型（好处：不用担心写窄了把 `read_file` 挡掉），
也别指望它做安全边界 —— **硬约束只有 hook**（M0 §4.5）。已记入 `questions-for-atomgit.md` A7。

### 5.2 ⚠️ 踩坑：`.hooks.json` 不许写注释，而且解析失败是**静默**的

第一版 `.hooks.json` 里写了 `//` 说明（`.mcp.json` 允许，就顺手也写了）。
结果整轮对话下来 `audit.jsonl` 一行都没有。诊断命令给的信号是自相矛盾的：

```
$ atomcode hooks list
Loaded Hooks:
  (No hooks loaded)
Hook Config Files:
  ✓ Project:  /workspace/.hooks.json     ← 文件找到了，却一条都没加载
```

根因在上游 `cc_hooks.rs:174`：

```rust
let Ok(parsed) = serde_json::from_str::<HooksFile>(&raw) else {
    return Vec::new(); // malformed → skip the file rather than wedge startup.
};
```

裸的 `serde_json::from_str`，**不剥注释**；解析不过就当没有 hook，不报错也不打日志。

**修法**：`.hooks.json` 改成严格 JSON，说明文字放进一个 serde 会忽略的 `_说明` 键；
`hca-init.py` 铺这个文件时顺手 `json.loads` 校验一次，不合法就打一行醒目的错。
已记入 `questions-for-atomgit.md` A5。

顺带一个反差：hook 的 `command` **不做**环境变量展开（`.mcp.json` 做），
所以 `${HCA_WORKSPACE:-/workspace}/.hooks/audit.sh` 必须由 `hca-init.py` 自己渲染
（`questions-for-atomgit.md` A6）。

### 6.1 端口与暴露：按总控端口表，两个服务都不对宿主

```yaml

  daemon:    expose: ["13456"]   # 不写 ports:，只在 compose 内网
```

所以容器里 daemon 听回环 **13457**，`socat` 在 `0.0.0.0:13456` 转发过去。

### 6.2 token：daemon 生成，启动脚本转发

任务书写的是"token 由启动脚本生成放共享卷"。实际做不到**生成** ——
5.1.0 的 `daemon` 子命令没有 `--token`，token 只能由 daemon 自己生成写进
`$ATOMCODE_HOME/daemon-<port>.json`。所以改成：**daemon 生成，entrypoint 抄到共享卷**。

```

```

共享卷 `hca_daemon-token` 里两个文件：`daemon-token`（裸 token）与
`daemon.json`（`{"base_url":"http://daemon:13456","token":"…"}`，省得调用方拼地址），
都是 0640。M2 的 web/api 只读挂载它即可。

## 7. 验收：6 个技能 × 一个真实问题

### 7.1 为什么走 `/live` 而不是任务书写的 `/chat`

M0 §5.4 已实测：**`/chat` 不挂载 MCP 工具**（模型可见 36 个工具，没有一个 `mcp__*`；
调用直接返回 `unknown or unmounted tool`），只有 `/live` 挂载（39 个）。
投研问题没有 MCP 就等于没有数据，在 `/chat` 上测"技能调用了哪些 MCP 工具"
会得到一个注定为空的答案。所以本轮改走 `/live`，这是待办池 P0-1 的既定结论。

问题取自各技能自己的 `hunter.prompt_tpl`（把 `{股票}` 换成真实标的），
**不明示让它用技能** —— 测的是"用户照着前端提示语问，模型会不会走到这个技能"。

每个用例开一个干净会话（`POST /sessions` + `POST /live/switch_session` + `POST /mcp/reload`，
原因见 §7.3），`permission_request` 由探针自动 allow 并记账。

### 7.3 ⚠️ 本轮最重要的发现：切会话之后 MCP 工具全部消失

前两轮跑批出现了一个说不通的现象：模型明明在 `9/9 connected` 的环境里，
却不调 MCP，改用内置 `bash` 跑 `python3 -c "import requests; …"` 自己去爬数据
（s6 那一轮连发 **26 次 bash**、烧掉约 **102 万 token** 也没拿到想要的东西）。

做了个受控实验：同一个 daemon、同一个问题（"你现在能调用的工具里，名字以 `mcp__`
开头的有哪些？"），只差一步。

| 步骤 | 模型自述可调的 `mcp__*` | 同一时刻 `/mcp/status` |
|---|---|---|
| 不切会话，直接问 | **28 个**（逐个列出来了） | 9/9 connected |
| `POST /sessions` + `POST /live/switch_session` 后问 | **0 个**（"当前运行环境中并未注册或挂载任何 MCP 服务工具"） | 9/9 connected |
| 再 `POST /mcp/reload`，**立刻**问 | 0 个 | 有 `connecting` |
| 再 `POST /mcp/reload`，**等到没有 `connecting`** 再问 | **28 个** | 9/9 connected |

根因应该和 M0 §5.4 的"`/chat` 不挂 MCP"同类：只有走 `wait_mcp_ready()` 的路径才等 MCP
就绪，`resume_session_with_lease` 不在其中。

**后果比"少几个工具"严重得多**：运维侧从 `/mcp/status` 上完全看不出异常，
模型却会退化成用 bash 自己爬数据，既慢又贵还不可靠。

**已验证的绕法**：切完会话后 `POST /mcp/reload`，**并且等到 `/mcp/status` 里没有
`connecting` 为止**。只 reload 不等是没用的。
探针已经这么改了；**M2 的 Web 转发层每次切会话都必须补这两步**。
记进待办池 P0-10 与 `questions-for-atomgit.md` B9。

### 7.4 权限：MCP 免确认，但内置 `bash` 照样弹

`.mcp.json` 的 `autoApprove` 只覆盖 MCP 工具。默认 `build` 档下，模型用内置 `bash` 跑
`python3 -c …` 这类命令仍会发 `permission_request`：

```json
{"type":"permission_request","tool_name":"bash","reason":"Requires approval",
 "arguments":"{\"content\":\"python3 -c \\\"import json; f=open('.mcp.json'); …\\\"\"}"}
```

第 2 轮跑批里没人应答它，**整轮挂了 300 秒**（探针超时才收场），
后续用例还被 `switch_session 被拒(active_turn)` 连带拖垮。
探针现在会自动 allow 并记账（最终一轮 6 个用例 0 次弹窗，因为模型没用到需要审批的 bash）。
**M2 的 Web 转发层必须把 `permission_request` 接到前端弹窗**，记进待办池 P0-9。

## 8. token 计量：`/live` 的数字基本不能用

任务书要求记录每个用例的 tokens。实测 `/live` 的 `tokens` 事件与 `state.stats`
**多数轮次是 0**：一条 12 轮的会话里 12 个 `tokens` 事件全是

`{"prompt":25610,"completion":43,"total":25653}`。看起来是网关只在部分响应里回 `usage`，
AtomCode 如实透传、不做累计。

所以 §7.2 表里的 token 列用的是**网关配额差值**（用例前后各查一次
`GET https://hunter.agentpit.io/api/saas/llm/quota` 的 `used_today`），这是真实计量。

**注意这是"最后一轮的 prompt"而不是整轮累计**，与配额差值差一个数量级。

比 M0 测的 16.3k 高了约 9k —— 多出来的正是 28 个 MCP 工具的 schema。
`cached_tokens` 普遍是 20,248，说明网关侧缓存在起作用。

## 9. 偏离任务书的决策汇总

| # | 任务书写的 | 实际做法 | 原因 |
|---|---|---|---|

  总控「前端完成的标准」不适用。

## 11. 交接给 M2

**可以直接用的：**

- `deploy/up.sh` 一条命令拉起，`--status` 看健康，`--down` 只删容器不删卷。
- daemon 在 compose 内网 `http://daemon:13456`，token 在共享卷 `hca_daemon-token`
  （`daemon-token` 裸 token / `daemon.json` 带 base_url），M2 的 web/api 只读挂载即可。
- `deploy/tools/dump_mcp_tools.py` 是排查 MCP 的第一手工具 ——
  `/mcp/status` 只会说 `MCP server closed stdout`，这个脚本给你 server 的 stderr 原文。
- `tools/probe/skill_e2e.py` 可以直接拿来跑评测用例（已处理会话隔离、权限应答、配额计量）。

**必须补的（按优先级）：**

1. **P0-10**：转发层每次切会话都要 `POST /mcp/reload` + 等 `connecting` 消失，否则丢全部 MCP。
2. **P0-8**：把 `apps/api` 纳入 compose（见 U-6），否则 6 个 hunter 系 MCP 一直是摆设。
3. **P0-9**：`permission_request` 接前端弹窗 + `POST /live/permission`，否则内置 bash 会把会话挂死。
4. **P0-7**：`stop_reason=stopped` 区分不了做完没做完，转发层要按任务完成度自行判断。
5. **P0-1 / P0-2**：转发层对接 `/live`；一个 daemon 只服务一个工作目录。
6. **P0-6**：llm-shim 的端到端收益必须在 M2 补做对照，做之前不许对外声称有收益。
7. **P1-3**：技能卡片要的 `display_name` / `icon` / `category` / `prompt_tpl`
   得自己读 `SKILL.md`，`GET /skills` 只回 name + description。

**M2 做领域改造时要知道的：**

- `.atomcode.md` 现在是占位版，底稿在 `reference/opencode/scripts-opencode/HUNTER-AGENT.md`。
- `allowed-tools` 不生效，**硬约束只有 hook**。
- 工作区镜像里 `ATOMCODE_VERIFY=off` 已经设上了（关掉"改完代码记得校验"那类编码向提醒）。
- `HCA_WORKSPACE_REFRESH=1` 时每次启动会用镜像里的模板重铺 `.atomcode.md` / 技能 / `.mcp.json`，
  调人设时要么改仓库重建镜像，要么临时设成 `0`。
