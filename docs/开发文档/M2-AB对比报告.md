## 6. 典型失败样例（原文）

### 6.1 `q2-thesis-review-opencode-r2`（基线（opencode 版））· 基线把题目退回给用户 —— 社区版没有「投研工作区」这个概念

```text
请提供您当初写下的**具体买入理由**以及设定的**证伪条件**文本（或关键要点）。收到后我将结合当前最新行情（现价约 46.80 元）与基本面数据，逐条为您复核评级与触发情况。
```

## 7. 结论与 fork 决策

总分比 **89.6%**（HCA 85.2 / 基线 95.1），闸门是 80% → **不 fork**。

## 7.1 先说结论

**总分比 89.6%（HCA 85.2 / 基线 95.1），高于 80% 的闸门 → 不 fork。**

补丁本身已经写好并在测试机上把上游四道门全跑过了（`docs/fork-patches.md`），
但它**不启用、不 fork、不提 PR** —— 闸门没触发就不做，这是总控「已拍板决策 4」的约定。

## 7.2 这个 89.6% 该怎么读

四个维度的走向完全不一样，把它们平均成一个数会丢掉全部信息：

| 维度 | HCA / 基线 | 说明 |
|---|---|---|
| A 准确性 | **97.1%** | 基本打平。HCA 唯一一次失手是 P0-11 的截断（见 §6.2） |
| B 工具调用正确率 | **103.5%** | HCA 略胜：工具调用成功率两边都是 100%，差别在 q4 的取证方式 |
| C 输出规范符合度 | **108.7%** | **HCA 明显胜出，而且这是唯一与工具清单无关的维度** |
| D 步数与耗时 | **52.0%** | **HCA 明显落后**，这一项把总分拉下来近 10 个点 |

### C 维度才是这次评测真正想测的东西

M2 的问题是「**不改内核，能不能让一个编码 agent 变成投研 agent**」。
A / B / D 三个维度都被「两边工具清单不一样」（HCA 9 个 MCP、基线 **6 个**，§4.3；
**「4 个」是 I2 实测更正掉的错数** —— 那次交叉核对的三处看的都是同一份
`.opencode/opencode.jsonc`，漏了工作区根下又注册了 `hunter_cap` 与 `screener`
的第二份配置。权威口径是 opencode 合并后的 `GET /config`，取证见
`docs/evidence/I2/社区版MCP清单-实测更正.md`。结论方向不变：HCA 多出来的是
`akshare` / `kronos` / `truesource` 三个）
和「两边工作区形态不一样」（§6.1）污染了；
**只有 C 维度与这两件事都无关** —— 它量的是「人设能不能压住内置的编码规则」。

C 维度 25.0 / 23.0，HCA 满分。逐项看：

- **C1 全中文**：两边 23 次运行全部 5 分，没有一次冒出整句英文。
  （AtomCode 内置人设是英文的，`## OUTPUT:` 段也用英文写规范 —— 这一项满分说明
  `.atomcode.md` 的语言约定压住了它。）
- **C4 不给买卖指令**：两边 23 次运行**全部 5 分，一次都没有命中**
  「建议买入 / 止损位 / 目标价 / 仓位建议」等 20 个模式。这是合规上最要紧的一条。
- **C5 判断附依据与风险**：HCA 12 次全 5 分；基线 11 次里有 4 次只有 3 分
  （q4 三次没写局限性、q5 两次纯罗列无风险表述、q2 一次 0 分）。
  差距主要来自 HCA 每篇末尾固定的 AI 生成标识与风险提示段 —— 那是人设里写死的。

**结论：领域改造在「输出规范」这个层面是成功的，而且是靠不改内核的四个外部面做到的。**

### D 维度落后是「做得更多」的代价，不是「做得更差」

D 是相对打分（两边中位数比），HCA 落后的直接原因是它每道题都做得更重：

| 题 | HCA 工具调用（中位数） | 基线 | HCA 墙钟（中位数） | 基线 |
|---|---|---|---|---|
| q1 单股基本面 | 7 | 2 | 47.2 s | 29.8 s |
| q2 持仓论点复核 | 22 | 2 | 106.0 s | 11.9 s |
| q3 因子筛选 | 1 | 1 | 14.8 s | 9.0 s |
| q4 Kronos | 1 | 0 | 9.8 s | 5.7 s |
| q5 情报汇总 | 18 | 3 | 93.3 s | 21.3 s |

q3 是最干净的对照：**两边都只调 1 次同一个 `market_screen`，都答出 313 只 / 5237 只，
前 10 只逐行相同** —— 工具清单一样时，两边的差距就只剩墙钟（14.8 s vs 9.0 s，引擎开销）。
q2 / q5 的巨大差距则来自 HCA 多出来的 akshare：它的 `search → signature → call`
三连是一次取数三次调用，而基线根本没有这个 MCP。

**所以 D 维度上的 52% 主要不是引擎慢，是工具清单不同导致的工作量不同。**
这一点评分表事先没能隔离 —— 它是这次评测设计上的一个已知不足，写在这里而不是藏起来。

## 7.3 这次评测查出来的四件实事

1. **P0-11（新，P0）**：MCP 返回超过 16 KB 被砍成头尾各 4 KB，阈值写死在
   `output_artifact.rs` 里、没有任何配置能改。HCA 侧 12 次运行里 **9 次工具返回被截断**，
   唯一一次 A1 判 0 正是出在截断最多的那一次。对投研这种数据密集场景，截断是常态不是例外。
   不改内核的绕法（压 MCP 返回 + 人设里写死「看到 truncated 必须先 fetch_output」）排 M3。
2. **P1-18（新）**：模型会绕过 MCP 层，直接 `bash python3 -c "import akshare…"` 自己取数。
   guard 按「只读/纯计算放行」的策略放行了，判定没错，但这条路径绕开了 MCP 层的全部治理。
3. **网关 07:50 的修复不是这批数据的混杂因素**（`tools/eval/check_parallel_calls.py`）：
   基线侧 5 组并行 `tool_calls`（q5 两次各 3 个）**全部被正确拆开**，修复前跑的那几次也一样。
4. **q4 证明了两边都不编**：本次环境确实没有 Kronos 的 key，两边 6 次运行
   **没有一次伪造预测价位或涨跌幅**。这是红线 1 在真实模型上的一次正面验证。

## 7.4 这批数据的边界（必须看见）

- **只跑了 23 次，不是计划的 30 次**，而且不是均匀的 3 次：
  q3 / q4 两边各 3 次，q1 / q5 两边各 2 次，**q2 是 HCA 2 次、基线 1 次**。
  原因是当日网关配额：本批实测一整轮（5 题 × 2 边、10 次运行）**1 314 569** token，
  开跑时只有 3 111 330，跑完两整轮后按「便宜的题优先」把剩余额度买成了完整的第 3 轮 q4 与 q3。
  **q2 基线侧 n=1 是这批数据最弱的一格**，结论里凡是依赖它的地方都已标注。
- **排除了 2 次运行**，都留了原始记录、都写明了理由：
  `q2-thesis-review-opencode-r1`（评测设置缺陷，`docs/eval/setup-defect/`）、
  `q1-fundamental-atomcode-r3`（配额见底被 HTTP 402 掐断，正文只有 273 字过程播报、
  没有结论，`docs/eval/incomplete/`）。
- **评分表有两处事后看不够好的地方**，按「评测前定好就不改」的规矩原样执行，但写明：
  ① q5 的 `needs` 里放了「持仓」，而题面已经把三只代码写全，持仓类其实不是必须的 ——
  两边 B1 都因此扣到 5.0，同扣不影响比较；
  ② D 维度没能把「工具清单不同导致的工作量不同」隔离出去（见 §7.2）。
- **fork 闸门因此偏松**：总分是「引擎 + 工具清单 + 工作区形态」的合成，
  而 HCA 在后两项上占优。**若只看与这两项无关的 C 维度，HCA 是 108.7%**；
  若只看工具清单相同的 q3，两边 A/B/C 全部打平、只有墙钟差 1.6 倍。
  也就是说：**没有任何一种读法会把结论推到 80% 以下**，不 fork 的结论是稳的。

## 7.5 fork 决策

**不 fork。** 依据：

1. 总分比 **89.6% ≥ 80%**（闸门），且四种读法（总分 / C 维度 / 同工具清单的 q3 / A 维度）
   没有一种低于 80%。
2. 领域改造要达到的目标（编码倾向被压住、输出规范成立、不给买卖指令、AI 标识与风险提示）
   **已经靠不改内核的四个外部面达成** —— C 维度满分是直接证据。
3. 唯一一处真正影响准确性的缺陷是 P0-11（工具返回截断），
   而它**不是 persona 能解决的问题**，那两个补丁开关（外部人设整体替换、让 `system_prompt` 生效）
   对它一点帮助都没有。也就是说：**就算 fork 了，这次评测里唯一的准确性失分也不会改善。**

补丁的技术部分与四道门的验证记录留在 `docs/fork-patches.md`，
标记为「已备好、未启用」。若后续里程碑出现 persona 层面真正压不住的问题，可以直接取用。
