# M4 成果与测试报告 · hook 全量 + 一键部署 + 回归 + 发布 v0.1.0

> 对应计划 v0.2 的 **TP-05（hook 全量）、TP-08（一键部署）、TP-10（回归、文档、演示）**。
> 测试机 `34.133.8.3`（Ubuntu 24.04 · 2 核 8G）。底座仍是 AtomCode **5.1.0 官方二进制**
> （`sha256 40d86fa3…`），**没有 fork**。
>
> 时间一律上海时间。所有数字来自真实调用，拿不到写 `—` 或「未测」+ 原因。
> ⚠️ 全程与另一条自驱链路（HunterLauncher）共用这台机器，load 长时间在 12～24，
> **本报告里的耗时都偏大**，不能当作正常机器上的性能指标。

## 1. 一句话结论

五组 hook（8 条注册）全部落地并在**部署好的容器里**逐条验过；
`deploy/install.sh` 从零装完一遍 **407 秒**（含 `next build`，镜像层部分命中本机缓存）、
升级与回滚各验一次；回归清单逐项有实测数字与证据；
文档补齐到能交给私募 IT 与二次开发者；v0.1.0 预发布已在 GitCode 与 GitHub 各发一份。

**这一轮真正的价值不在"按任务书做完了"，而在从零安装把三个藏了一轮的缺陷炸出来**：

| 缺陷 | 性质 | 怎么发现的 |
|---|---|---|
| `.gitignore` 里一行裸 `atomcode` 把 **M3 整个转发适配层**（5 个文件 1400+ 行）吞掉了，仓库里根本没有那份代码 | **任何人 clone 都构建不出来**（`Module not found: Can't resolve '../../../lib/atomcode'`） | 用 install.sh 从 GitHub clone 装第一遍，web 镜像构建直接失败 |
| `HCA_LLM_API_KEY_FILE`（文档里标「推荐」的那条路）**从来没跑通过** —— 容器里是 uid 10001，宿主上的 key 是 0600 owner=运维 | daemon 起不来，只留一段 `PermissionError` traceback | 同一次安装的下一步 |
| `GET /live?session_id=` 被一个**孤儿 runtime** 占住后，整个网页永久不可用，而 `/health` 与 `/mcp/status` 全绿 | 网页每条消息都 `upstream_unreachable`，运维无从下手；同一事故还让一轮烧掉 **982 548 token** | 回归里换一条链路验证时撞到 |

三个都已修并有回归用例。**M3 报告里「Playwright 10/10」是真的**——
那套代码在测试机上靠 rsync 存在，只是从来没进过仓库；这正说明"真部署"和
"从仓库从零装"是两件不同的事，只做前者会漏掉整整一类问题。

## 2. 偏离计划的决策与原因

| # | 决策 | 原因 |
|---|---|---|
| D-1 | **hook 是五组、8 条注册**，不是任务书说的"四个" | 任务书列的是 audit / guard / lang / budget 四类职责。M2 已有的 `context`（注入真实日期与交易时段）不能丢，所以实际是 5 组实现；又因为 audit 要同时接 `PostToolUse` 与 `PostToolUseFailure`、budget 要同时接 `UserPromptSubmit` / `Stop` / `StopFailure`，`.hooks.json` 里是 **8 条注册**。清单见 `docs/hooks-design.md` §1 |
| D-2 | **audit 的"参数摘要"与"耗时"由 guard 落一份起始记录，audit 来配**，没有单独挂 PreToolUse 的 audit hook | 上游 PostToolUse 的 payload 里**既没有 `tool_input` 也没有耗时，而且两个事件都不带 `call_id`**（`cc_hooks.rs:763-903`），没有任何字段能把 pre/post 配起来。guard 本来就每次 PreToolUse 都跑、手里正好有参数；再挂一个 hook 等于每次工具调用多起一个 python 进程（实测单进程约 80～330 ms）。配不上就写 `null` + `"—"`，不猜 |
| D-3 | **lang 只实现了提示词侧那一道**，出口强校验记为 P1-21 | 原 opencode 的 `hunter-lang` 插件挂在 `experimental.text.complete`（出口）。AtomCode 的 8 个事件里**没有"助手正文写完"这个点**：PostToolUse 能改的是工具返回，Stop 时回答已经流给用户了。落点已想清楚（Web 转发层 + api 现成的 `/api/internal/lang/guard`），但任务书第 1 条只要求 hook 侧，**不在这一轮悄悄扩范围**。现状风险评估见 `docs/hooks-design.md` §5 |
| D-4 | **budget 默认关闭，且"token 未知时不拦"** | TP-05 原文是「默认关，与现状一致」。公开仓里本来就没有 budget 插件（`hunter-community/scripts/opencode-mcp/plugins/` 只有 lang 与 mcp-context 两个，全仓 grep `budget` 无第三个；私有仓按总控约束不看不抄），所以"与 opencode 版一致"= 不改变现有行为。把默认改成会拒绝用户，属于偷偷改产品语义。<br>另外 token 有两个真实源都可能缺（见 §3.3），拿不到时**不按 token 拦** —— "不知道" ≠ "超了" |
| D-5 | **顺手落地了总控新增的已拍板决策 9、10** | 那是 M3 的 U-10 / U-11 的答复，写进了总控规则。两条都只改转发层、前端零改动（决策 1）。不做的话它们会一直悬着，而 M4 的回归本来就要过界面 |
| D-6 | **Ollama 通道「未测」** | 测试机磁盘只剩 12～14G（91%）且与另一条链路共用，`ollama/ollama` 镜像加一个模型要 2G+，**填满磁盘会连带弄坏别人的链路**，风险不对等。已中止镜像拉取。改为：install.sh 的 ollama 分支用一个**真实的** OpenAI 兼容端点验证校验逻辑（见 §4.6），Ollama 本体未在真机上跑过 |
| D-7 | **macOS 只做脚本审阅** | 任务书明确允许。`install.sh` 里有 Darwin 分支（`sw_vers` 取版本、Ollama 用 `host.docker.internal`、提醒 Docker Desktop 内存），但**没有真机** —— 脚本里也会显著打印"没有在真机上跑过" |
| D-8 | 一次性把 M2 的基线栈（`hca-baseline`，5 个容器）停掉 | A/B 评测已收尾，它白占 2 核机器的 CPU 与内存，而回归要跑真实模型。只 `stop`、**卷全部保留**，要复现 A/B 再 `start` 即可 |

## 3. 做了什么（对应计划哪节）

### 3.1 TP-05 · hook 全量（`distro/workspace-template/.hooks/` + `.hooks.json`）

五组实现、8 条注册，逐条职责与上游契约见 [`docs/hooks-design.md`](../hooks-design.md)。本轮新增/改动：

**guard 补齐四个真实绕过**（都是先读上游源码找出来、再写成单测，最后**逐条对 M3 那版复验**）：

| 口子 | 旧版行为 | 依据 |
|---|---|---|
| `bash_start`（后台 shell） | 完全不判 —— 同一条 `rm -rf holdings/` 用 `bash` 被拒、丢到 `bash_start` **直接放行** | 上游 `tools/mod.rs:210` 无条件注册 `bash_start`/`bash_poll`/`bash_kill`，`bash_start` 的参数名和 `bash` 一样是 `command`（`bash.rs:453`） |
| 直接调取数库（P1-20） | `import akshare as ak; ak.stock_zh_a_daily(...)` 漏过 —— `INLINE_NET_RE` 认的是"谁在发 HTTP"，而 akshare 是自己在内部发 | M3 的 Playwright 真拍到过模型这么绕 |
| 包装命令与 `sh -c` | `env X=1 rm -rf /`（首词是 `env`）、`timeout 5 rm`、`sh -c "rm -rf x"`（子命令整条在引号里）全部漏过 | shell 语义 |
| 中间带 `..` 的越界路径 | `cat holdings/../../etc/passwd` 漏过 —— 旧判据只认「以 `/` `~` `../` 开头」 | shell 语义 |

复验结果（`docs/evidence/M4/guard-old-vs-new.txt`，脚本 `tools/hooks/guard_old_vs_new.py`）：
**7 条真实绕过旧版全部漏过、新版全部拦住；3 条反误伤对照（纯计算 / 只读 cat / 写 reports）两版都放行。**

**audit 记全六项**：工具名、参数摘要、耗时、结果大小、会话、用户标识；
`PostToolUse` 与 `PostToolUseFailure` 同一份实现（按 `hook_event_name` 分流，`ok` 字段区分）；
本地同步追加（不 fsync、不读旧内容）+ 超过 `HCA_AUDIT_MAX_MB` 轮转一代；
可选异步上报走**脱离进程组**的子进程（上游超时会 `kill_on_drop` 连子进程一起杀，不脱离就白搭）。

**lang**：规则原文与 `apps/api/agents/text_sanitizer.py:74` 的 `ZH_ONLY_RULE` **逐字一致**，
单测去读那个文件比对 —— 这是"改一处漏一处"的闸。

**budget**：Stop/StopFailure 记账 + UserPromptSubmit 超限拦截，默认关。

**顺手做的性能修正**：容器里实测 `python3` 空转 **82 ms**、
多一个 `import urllib.request` 变 **498 ms**、`import subprocess,tempfile` 变 **258 ms**，
而 guard/audit **每次工具调用都要跑一遍**。把 urllib / shlex / subprocess / tempfile
挪进真正用到它们的函数之后（数字是真实 `atomcode hooks test` 报的 Duration）：

| hook | 优化前 | 优化后 |
|---|---|---|
| guard（PreToolUse） | 573 ms | **330 ms** |
| audit（PostToolUse） | 567 ms | **201 ms** |
| audit（PostToolUseFailure） | 594 ms | **176 ms** |
| budget（Stop） | 1 098 ms | **185 ms** |
| lang / context（UserPromptSubmit） | 94 / — ms | 101 / 189 ms |

单次工具调用的 hook 开销从约 **1.14 s** 降到约 **0.53 s**（guard + audit 两跳）。

### 3.2 TP-08 · 一键部署（`deploy/install.sh`）

一个脚本管装 / 升 / 回滚 / 看状态，两种用法：**在仓库里跑**（直接用当前代码）或
**单独下载一份跑**（自己 `git clone`，GitCode 拉不动自动换 GitHub —— 美国机房访问
GitCode 的 HTTPS 会 418，这条回退路径在测试机上真跑过）。

流程：环境检测（docker / compose v2 / curl / python3 / 内存 / 磁盘，macOS 显著标注未真机测试）
→ 选安装目录 → 取代码 → **模型通道三选一**（默认 OneAPI · Gemini 3.8）→ **真实打接口校验 key**
→ 写 `deploy/.env`（0600）+ key 只落 `secrets/llm-key`（0600）→ 拉起（复用 `deploy/up.sh`）
→ 健康自检 → 把**容器里生效的那份** `config.toml` 抄出来（api_key 打码）→ 打印访问地址与管理员口令文件位置。

几个有意的设计：

* **key 校验是真调用**：oneapi 走 `/quota`（把今日已用 / 上限 / 剩余按响应原样打出来），
  official / ollama 走 `/models` 并核对模型名在不在列表里。校验不过**默认拒绝安装**，
  离网可用 `--allow-unverified-key`（会显著警告）。
* **config.toml 不在宿主上重新渲染一遍**：真正生效的那份是 daemon 容器启动时按 `.env` 渲染的
  （`deploy/daemon/hca-init.py`）。install.sh 把容器里那份抄出来打码保存，避免"两处实现、改一处漏一处"。
  （顺带发现：daemon 启动后会把上游那份几百行的注释模板写回 config.toml，所以打印时只打有效行 —— P2-13。）
* **多套并存**：compose 项目名改成可配（`HCA_COMPOSE_PROJECT`，默认 `hca`；容器名与**数据卷**都按它隔离），
  镜像 tag 也可配（`--image-tag`）。测试机上因此能起一套临时栈做「从零安装」验证而不碰主部署。
* **升级前自动存回滚点**（当时的 commit + 当时的 `.env`），自检不过会明确给出回滚命令；
  **回滚只回代码与镜像，库结构留在新版**（本项目迁移都是加表加列，旧代码能跑），这一点在脚本里与文档里都写明。
* **国内网络**：三个自建镜像加 `BASE_IMAGE_PREFIX` / `NPM_REGISTRY` / `PIP_INDEX_URL` 构建参数
  （默认空 = 与之前逐字等价）。daemon 取官方二进制那一步**换源后 sha256 校验照旧** ——
  镜像源上的包对不上就构建失败，这是有意的。

### 3.3 预算 hook 的 token 从哪来（实测，不是设计意图）

Stop 的 payload 里没有 token。两个真实源：

1. **会话 `.meta` 的 `turn_stats`**（按会话精确）。测试机主部署一份真实会话（`fdc426fd…`）的原文：
   `tool_call_count` / `duration_ms` 可靠；**`total_tokens` 恒 0**（与 P1-12 同一根因）；
   `model_usage` **只有部分 turn 有** —— 那次会话 turn 1 有（input 17038 / output 40 / cached 0），
   turn 2 整个字段都不在。所以 budget **只有覆盖率 100% 才拿它当 token 源**，
   并在记录里写明 `meta_turns` / `meta_turns_with_usage`。
2. **网关配额差值**（兜底，按 key 全局）：`GET $HCA_QUOTA_URL` 的 `used_today` 差值，
   与 M2 评测算成本用的是同一个口子。单工作区私有化部署下就等于这套栈的用量；key 被别处共用会偏大。

两个都拿不到 → token 写 `null` 且不按 token 拦。工具调用次数一路可靠，硬限额优先用它。

### 3.4 落地已拍板决策 9 / 10（都在转发层，前端零改动）

* **决策 9**（选择器要让人看懂切的是**审批档**不是换助手）：适配层把它暴露的 name 改成
  「投研助手 · 审批档 build」，description 写明「切的是能否写文件、**全局生效**、
  真正的边界由 guard hook 守」。前端把 name 显示在按钮上、description 显示在下拉项里，
  所以这两段文字就是那个"标注"；opencode 那条分支的语义不受影响（它那边确实是 agent）。
* **决策 10**（接受同一时刻只跑一个回合，但**忙时要有明确提示**）：回合本来串在
  `state.turnChain` 上，第二个人发消息时界面**什么都不动**。现在入队那一刻就把用户消息
  和一条排队说明推给他（共用同一个 assistant 消息 id，否则界面上会冒出两条助手消息），
  并把超时计时从"入队"改成"真正开跑"（否则排在后面的回合会把超时预算耗在等待上）。
