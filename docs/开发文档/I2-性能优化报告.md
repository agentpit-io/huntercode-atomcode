## 1. 先把时间拆清楚

### 1.1 量化手段（三份互相独立的记录）

M2 的报告只知道「q3 两边都调 1 次 `market_screen`，HCA 14.8 s、社区版 9.0 s」，
但 14.8 秒花在哪一段说不出来。I2 先补了三样东西，都是这一轮新写的：

| 手段 | 位置 | 量到的东西 |
|---|---|---|
| **llm-shim 请求追踪** | `scripts/llm-shim/shim.py`（`SHIM_TRACE_DIR`，默认关） | 每次发往网关的请求：消息与工具 schema 的尺寸构成、上游首字与总耗时、网关回的 `usage`。**只记长度与工具名，不记正文、不记 Authorization** |
| **SSE 段落切分** | `tools/eval/eval_atomcode.py` 的 `waterfall()` | 每个 SSE 事件打相对毫秒，切成「首轮模型调用 / 工具执行 / 下一轮模型调用 / 收尾」 |
| **hook 基准** | `tools/eval/hook_bench.py` | 在容器里按 hook 真实的调用方式直接跑、取中位数 |

**一处归因更正**：PreToolUse / PostToolUse 的耗时**不在 SSE 的工具段里**。
pilot 实测工具段 1 157 ms、工具自己报的 `duration_ms` 1 156 ms —— 差 1 ms，
说明上游是在发出 `tool_start` **之前**跑 PreToolUse、在 `tool_result` **之后**跑
PostToolUse，两跳都落进了相邻的「模型段」。所以 hook 只能单独量，
瀑布表里那一行如实改叫「工具段余量」。

### 1.2 一轮请求里到底装了什么（实测）

q3 单题试跑（`docs/eval/i2/pilot/`，2026-09-22 13:32 UTC）的第一条上游请求：

| 构成 | 实测 |
|---|---|
| 工具个数 | **59 个** |
| 工具 schema 合计 | **59 885 字节** |
| 系统提示 | **30 991 字符**（三条 system 消息：AtomCode 内置人设 20 855 + 会话上下文与我们的项目指令 7 199 + 技能清单 1 450，取自 M2 的 `/live` snapshot） |
| 整个请求体 | 129 574 字节 |
| 网关回的 `prompt_tokens` | **26 132** |

工具 schema 里最大的那几个（同一次请求）：

| 字节 | 工具 | 本场景用得上吗 |
|---|---|---|
| 4 396 | `mcp__screener__market_screen` | 用得上（描述 2 184 字） |
| **3 738** | `atomgit_pr` | 用不上 |
| **2 372** | `code_review` | 用不上 |
| 2 325 | `mcp__uzi__stock_deep_analysis` | 用得上 |
| 2 232 | `read_file` | 用得上 |
| **1 750 / 1 155 / 943** | `atomgit_repo` / `atomgit_issue` / `atomgit_api` | 用不上 |
| **997 / 626 / 605 / 542 / 483 / 480 / 445 / 416 / 400** | `ast_grep` / `read_symbol` / `list_symbols` / `find_references` / `trace_callers` / `trace_callees` / `blast_radius` / `file_dependencies` / `trace_chain` | 用不上 |
| **1 141 / 727 / 587** | `recall` / `list_sessions` / `schedule_wakeup` | 用不上 |

合计 **17 407 字节（占工具 schema 的 29%）是投研场景一次都用不上的**，
而它们**每一轮**都要重发一遍。

### 1.3 一次对话里有一条「白付」的模型请求

同一次 q3 试跑，shim 追踪里有**三条**上游请求，而这道题只有 2 轮：

| # | 工具数 | 消息 | 上游总耗时 | 是什么 |
|---|---|---|---|---|
| 1 | 59 | system + user | 6 032 ms | 第一轮（模型决定调 `market_screen`） |
| 2 | 59 | system + user + assistant + tool | 7 861 ms | 第二轮（拿到数据后写答案） |
| 3 | **0** | 只有一条 1 055 字的 user | **3 817 ms** | **会话自动起名** |

第三条就是 SSE 瀑布里那段 4 738 ms 的「收尾」。上游在每轮对话结束后会**再发一次
模型请求**给会话起标题（`ATOMCODE_AI_SESSION_NAMING`，`atomcode-config/src/config/mod.rs:1733`）
—— 而本发行版的会话标题是 Web 侧自己管的，这一跳纯属白付。

### 1.4 hook：每次工具调用要等将近一秒

`tools/eval/hook_bench.py`，测试机空闲时（load ≈ 1）在一次性容器里跑，
每个 hook 预热 2 次后取 9 次的中位数（原始记录 `docs/eval/i2/hook-bench/`）：

| hook | 事件 | I2 之前 |
|---|---|---|
| guard | PreToolUse | **675 ms** |
| audit | PostToolUse | 241 ms |
| context | UserPromptSubmit | 268 ms |
| lang | UserPromptSubmit | 142 ms |
| budget | UserPromptSubmit | 244 ms |
| **每次工具调用（guard + audit，一前一后串行）** | | **966 ms** |
| **每条提问（UserPromptSubmit 那几条上游是并发跑的，付最慢那条）** | | **292 ms** |

（4 次独立跑的中位数；单次之间有几十毫秒的漂移，2 核机器上正常。）

guard 为什么比别的贵一截：`python -X importtime` 显示 `urllib.request` 累计
**532 ms**（主要在 `http.client` → `email.parser` 那一串），而它被写在
`lookup_user()` 的开头、**在查缓存之前** —— 缓存命中率再高也照样每次付。
另外，没有会话归属记录的会话（评测探针自己 `POST /sessions` 建的那种）
每次都要再打一遍 api 拿 404，然后照样落到 `HUNTER_USER_ID` 兜底。

M4 报告里记的是 guard 330 ms —— 那是 M4 当时在部署好的容器里用
`atomcode hooks test` 量的，payload 不同（没走到身份反查那一支）。两个数都没错，
量的不是同一条路径；I2 这里用的 payload 是**真实评测里最常见的那一种**
（`mcp__watchlist__stock_quickview`），所以贵。

## 2. 优化手段与逐项实测

六项，每一项都能单独关掉（开关见 `docs/部署与运维.md` §6.3），
默认值就是实测下来最快的那一组。

### 2.1 组合工具（新 MCP `hcapack`）

**为什么是最大头**：每多调一次工具就要**多跑一轮模型**，而每一轮都把整段上下文
重发一遍。M2 实测 q2 用了 22 次调用 / 106 秒 / 67 万 token，根因有两个：
`akshare` 的 `search → signature → call` 三连（一次取数三次调用）、
以及「三只票逐只单独查」。

新增三个工具，一次调用返回一道题要的整包数据：

| 工具 | 一次拿到 |
|---|---|
| `stock_snapshot(code)` | 最新价与数据时点、营业总收入与归母净利润及各自同比、扣非净利润、毛利率、ROE、资产负债率（最近 5 个报告期） |
| `stocks_intel(codes, limit)` | 每只票的近期新闻（带来源与**日期**）+ 一手信号简报 |
| `thesis_evidence(code)` | 论点原文 + 持仓账本 + 行情 + 财务 + 最近几次分红 |

三个工具的 schema 合计只有 **2 200 字节**。

数据来源都是真取的，每一块带 `source`，子调用失败就在那一块写 `error`
并保留其余块 —— **不拿别的数据顶上、不留空让模型去猜**（总控红线 1）。
财务走 AKShare `stock_financial_abstract`（新浪源）；
**东方财富系 `*_em` 接口在本机房实测拉不通**（`stock_bid_ask_em` /
`stock_individual_info_em` 都返回空体、JSONDecodeError），所以不用它们。

**真跑探针实测**（`tools/probe/pack_mcp_probe.py`，直连 stdio、不经模型、
不烧 token；测试机一次性容器）：

| 工具 | 串行版 | 改并行后 | 返回字节 |
|---|---|---|---|
| `stock_snapshot("601088")` | 11 294 ms | **4 161 ms** | 2 143 |
| `stocks_intel("600519,601088,300750")` | 8 791 ms | **5 228 ms** | 6 472 |
| `thesis_evidence("601088")` | 14 323 ms | **2 236 ms** | 3 153 |

探针还抓出两个必须修的：

1. **组合工具返回的新闻全都没有日期**。P1-17 的日期补洞原先只写在
   `watchlist_mcp.py` 里，组合工具直接打同一个后端接口、走的是另一条路。
   而 q5 题面明确要求「每条都要给出来源与日期」—— 不修的话这一项是拿 A 维度的分
   去换 D 维度的分。已把补洞挪进 `hca_news_date.py`，两边共用一份。
2. **子调用是串行的**。一次调用里仍然是几个互不依赖的取数（行情打后端、
   财务打 AKShare、分红打巨潮），串着跑白等。改成线程池并行。

### 2.2 工具白名单（llm-shim 这一跳）

AtomCode 把编码工具、代码智能工具、AtomGit REST 工具**无条件** mount 给模型
（`atomcode-coding/src/assemble.rs:225` 的 `mount_coding_tools`），
**没有任何 config 或环境变量能关** —— 这一条是这一轮翻上游源码确认的。

所以做在我们自己的那一跳：`LLM_TOOL_DENY` 按名字/前缀把 §1.2 列出的 17 个工具
从请求里摘掉（`atomgit_*`、代码智能一族、`recall` / `list_sessions` /
`schedule_wakeup`）。**只做减法，其余字段一个不碰；内核那边仍然注册着**，
万一模型凭记忆硬凑一个调用照样能执行，不会出现「说有却调不动」的死角。

省下 **17 407 字节 / 59 885 字节 = 29% 的工具 schema**。

> **这一节在 §5 之后要改口一半。** 「没有任何 config 能关」在官方 5.1.0 上依然成立，
> 但本轮的 fork 补丁给上游补了这个口子（`[tools] allow` / `deny`），所以 fork 那两条线上
> 这些工具是**根本不挂**，不是「挂了再由 shim 摘掉」。两层都留着：官方二进制上
> 只有 shim 那层可用，而 shim 那层摘的是请求，daemon 侧仍然认得这些工具。

### 2.3 关掉会话自动起名

`ATOMCODE_AI_SESSION_NAMING=0`。省掉 §1.3 那条**整整一次模型请求**
（实测 3 817 ms）。本发行版的会话标题由 Web 侧自己管，这一跳没有任何用处。

### 2.4 hook 提速（两步）

**第一步 · guard 身份反查**：把缓存查挪到 `import urllib` **之前**
（那三个 import 在容器里实测 530 ms），并给 404 加 60 秒负缓存
（没有归属记录的会话原先每次工具调用都要重新打一遍接口）。
网络错误**不**写负缓存 —— 临时故障不能被记成「这个会话没有身份」。

**第二步 · hook 常驻服务**：上游每触发一次 hook 就 spawn 一次 `command`
（`cc_hooks.rs`），而 guard + audit 是**每次工具调用都要跑**的两个 python。
新增 `hookd.py` 把五个 hook 预加载进一个常驻进程，`.sh` 包装改成
**bash 客户端**（`/dev/tcp` 走容器内回环，不再起 python）。
判定逻辑一个字没改 —— 服务端调的就是同一份 `guard.py`。

**实测**（一次性容器、测试机空闲、每个 hook 预热 2 次后取 9 次中位数，
4 次独立跑再取中位数；原始记录 `docs/eval/i2/hook-bench/`）：

| hook | I2 之前 | 只改 guard 缓存 | + 常驻服务 |
|---|---|---|---|
| guard（PreToolUse） | 675 ms | **242 ms** | **26 ms** |
| audit（PostToolUse） | 241 ms | 272 ms | **25 ms** |
| context（UserPromptSubmit） | 268 ms | 293 ms | **33 ms** |
| lang（UserPromptSubmit） | 142 ms | 167 ms | **17 ms** |
| budget（UserPromptSubmit） | 244 ms | 217 ms | **17 ms** |
| **每次工具调用（guard+audit）** | **966 ms** | **510 ms** | **51 ms** |
| **每条提问（并发取最慢）** | **292 ms** | **293 ms** | **34 ms** |

对照任务书给的两个目标：**每次工具调用 ≤ 0.1 s → 实测 51 ms ✓**；
**UserPromptSubmit 总耗时 ≤ 0.2 s → 实测 34 ms ✓**。

「只改 guard 缓存」那一列里 audit / context / lang 比基线还慢几十毫秒 ——
那是 2 核机器上的跑间漂移，不是回归（这三个的代码这一步没动）。

安全上的底线：客户端连不上服务、或服务端答不出状态行时，**一律退回原来的
「自己起一个 python 跑一遍」**。guard 是本发行版唯一的硬约束，只能 fail-safe。
`HCA_HOOKD=0` 可以整条关掉。

单测里逐条比对了两条路径的判定（放行、越界写、取数命令、工作区外读），
并验了「服务不在时仍然 deny」「16 个并发请求互不串扰」。
**并发那条用例第一次跑就抓到一个真 bug**：`run_hook` 换的是全局
`sys.stdin`/`sys.stdout`，两个请求同时进来会互相抢 —— 而 UserPromptSubmit 的
几条 hook 上游本来就是并发触发的（`cc_hooks.rs:636`），生产里必然踩到。已改成串行。

### 2.5 MCP 子集开关

`HCA_MCP_DISABLE` —— 铺 `.mcp.json` 时按名字去掉 server。两个用途：
I2 的 A 线对照（把 HCA 压成与社区版相同的 4 个 MCP），
以及产品侧「用不上的数据源关掉能省下一整块工具 schema」。
不设这个变量时**一个字都不改**（原样铺、注释与 `${VAR}` 都留着由 AtomCode 展开）。

### 2.6 上下文瘦身（人设）

`.atomcode.md` 第七节原先是一张 1 950 字的表，逐条说明「AtomCode 那些编码规则
在这里不适用」—— 其中大半说的是**已经被白名单摘掉、根本不会出现在工具清单里**
的工具。压成一段 + 7 行表。第五节反过来加了组合工具的引导与并行取数的判断标准
（「后一个调用的参数不依赖前一个的返回，就并行发」），以及「技能是给
『要一份成型报告』的请求用的，普通取数问题直接用组合工具」——
M2 的 q1 就是被 `use_skill(deep_analysis)` 带成 5 次调用的，
而技能的 `allowed-tools` 里没有组合工具。

净变化 8 155 → 7 857 字符。这一项的价值主要不在省字节，在**改变模型的取数路径**。

### 2.7 两条与网关有关的实测（决定了哪些优化值得做）

跑在测试机上、直接打网关，不经 daemon（原始记录 `docs/eval/i2/latency/`）。

**（a）llm-shim 这一跳要多少钱：几十到两百毫秒**。同一个小请求交错各跑 8 次，
两次独立测量：

| 测量 | 直连网关（总耗时中位） | 经 llm-shim | 差 |
|---|---|---|---|
| 第一次（各 7/6 次有效，末尾撞上网关 429） | 2 584 ms | 2 651 ms | **+67 ms** |
| 第二次（各 8 次全有效） | 2 397 ms | 2 610 ms | **+213 ms** |

两次差得不小（网关本身的抖动就有一两百毫秒），所以只给区间、不给一个精确值。

计划里写着「评估 llm-shim 一跳能否去掉」。**实测下来不该去**：67 ms 相对于
一次 2.5～4 秒的模型往返仍然是小头，而这一跳正是工具白名单（§2.2，省 29% 工具 schema）
唯一能做的地方 —— 去掉它等于把那一项也一起扔了。llm-shim 的另一个职责
（并行 `tool_calls` 补 index）虽然已被网关侧修好（决策 6），但保留作兜底也没有代价。

**（b）省 token ≠ 省时间** —— 这一条改变了后面几项的优先级：

| 系统提示 | 实测输入 token | 首字中位 ms | 总耗时中位 ms |
|---|---|---|---|
| ≈0（对照） | 143 | 2 759 | 2 802 |
| ≈1.5 万字符 | 13 515 | 3 956 | 3 998 |
| ≈3 万字符 | 27 026 | 3 896 | 3 941 |

**从 1.35 万 token 涨到 2.7 万 token，首字延迟没有变化**（3 956 → 3 896 ms；
第二次独立测量 3 908 → 3 888 ms，两次都是「更长反而略快」，说明差值在噪声里）。也就是说：

- 工具白名单与人设瘦身（§2.2 / §2.6）**主要省的是成本，不是时间**。
  这两项照做（token 中位数是本轮的验收口径之一，而且上下文越干净模型越不容易跑偏），
  但**不能指望它们把墙钟拉下来** —— 报告里不会把省下的 token 折算成秒。
- 真正吃墙钟的是**模型往返的次数**：一次往返在这个通道上的地板价就是 2.5～4 秒。
  所以 D 维度的钱要花在「少跑几轮」（§2.1 组合工具）与「别多跑一轮」（§2.3 会话起名）上。

对照 M2 的 q3（两边都是 2 轮、都只调 1 次 `market_screen`，HCA 14.8 s vs 基线 9.0 s）：
差的 5.8 秒基本可以被这三项解释 —— 会话起名 3.8 s + hook 两跳约 1.0 s +
发请求前的装配。三项在本轮都已处理。

## 3. 复测怎么做的

### 3.1 四个批次

| 目录 | 阶段 | 二进制 | HCA 侧挂了什么 | 开关 |
|---|---|---|---|---|
| `docs/eval/i2/baseline-b/` | I2 之前 | 官方 5.1.0 | 9 个 MCP | 白名单空、会话起名开、hook 每次起 python |
| `docs/eval/i2/baseline-a/` | I2 之前 | 官方 5.1.0 | **与社区版相同的 6 个** | 同上 |
| `docs/eval/i2/opt-b/` | 四个外部面 | 官方 5.1.0 | 10 个 MCP（含 `hcapack`） | 白名单开、会话起名关、hook 常驻 |
| `docs/eval/i2/opt-a/` | 四个外部面 | 官方 5.1.0 | 与社区版相同的 6 个 | 同上 |
| `docs/eval/i2/opt-fork-b/` | 外部面 + fork | **自编 fork** | 10 个 MCP | 同 opt，另加人设整体替换 + `[tools] deny` |
| `docs/eval/i2/opt-fork-a/` | 外部面 + fork | **自编 fork** | 与社区版相同的 6 个 | 同上 |

题目与评分表**逐字沿用 M2**（`tools/eval/questions.py`）。每个批次
5 题 × 2 边 × 3 轮 = 30 次，**A/B 交错且每轮换先手**。

`opt` 与 `opt-fork` 之间**只差那一层二进制和它才认得的两个 config.toml 参数**
（`deploy/eval/docker-compose.i2-fork.yml` 是唯一的额外覆盖）：工作区模板、
MCP 清单、hook、llm-shim 白名单全部相同。这样「fork 值不值」这个问题是可以
单独回答的，不会和四个外部面的收益混在一起。

三件事是这一轮刻意固定住的：

1. **六个批次共用同一个镜像**（fork 那两个是在它之上叠一层换二进制，
   见 `deploy/Dockerfile.daemon-fork`），差异全在挂进去的工作区模板与几个开关上
   （`deploy/eval/docker-compose.i2.yml` 的 `HCA_I2_TEMPLATE`）——
   这样「优化前 vs 优化后」比的是改动本身，不是两次构建。
   为此 `hca-init.py` 也改成从宿主目录挂载：fork 阶段要多渲染 `[tools]` 那一段，
   若靠重建镜像来带这段代码，基线与优化就成了两次构建的产物。
   开关是否真的传进去了，用 `docker compose config` 逐个组合核过（不起容器，只解析配置）；
   fork 阶段起栈后还会把 `config.toml` 里那两项**回显出来** —— 参数写了但二进制不认
   是这一档最容易悄悄发生的事。
2. **A 线是「与社区版相同的 6 个 MCP」，不是 M2 §4.3 写的 4 个** ——
   见 §6 的更正。人设里那段「优先用组合工具」也会跟着一起裁掉
   （`<!-- hca:if-mcp hcapack -->`），否则等于叫模型去调一个它看不见的工具，
   A 线量到的就不是引擎了。
3. **评测期间 `KRONOS_API_KEY` 留空**，与 M2 同口径。理由写在
   `docs/eval/i2/README.md`：q4 考的是诚实度，而社区版根本没有预测类 MCP ——
   只给一边一把能用的 key，比的就成了「谁有 key」。

### 3.2 哪些分是算出来的，哪些是人判的

**D 维度（D1 步数 13 分 / D2 墙钟 12 分）是纯自动项**，从原始记录直接算，
口径与 M2 评分表逐字相同（两边各取自己 3 次的中位数，较小者作基准）。
`tools/eval/i2_compare.py` 跨批次并排算，拿 M2 的 `docs/eval/raw/` 回跑校验过 ——
逐题中位数与 M2 报告 §7.2 的表**逐格相同**。

A / C 里的人工项按 M2 同一套表打分，每一条理由都写进 `manual-scores.json`
并能回到原始记录；**人工项没填的那一次整次不出分**（不补默认值）。
A1 用 `tools/eval/audit_numbers.py` 把正文里每个数字与本次工具返回对一遍 ——
它**不给分**，只把需要人看一眼的那几个挑出来。

### 3.3 这批数据的条件

**换过一次机器，第一批数据整批作废。** 原本按计划在测试机 hunter-test-01
（2 核 8G）上跑，2026-09-23 00:44 查实那台的 load average 在 **17–22** 之间
（HunterLauncher 在同一台上跑 Tauri GUI 测试 + 5 套服务栈里 3 套 opencode），
同一道 q4 在那种负载下 AtomCode 侧一次 **133 秒**（M2 同题 9.8 秒）。

`baseline-b` 批次连栈都没起起来（日志只有一行「✗ 起栈失败」，没有数据）。
之后**新开了专用评测机 hca-bench-01**（e2-standard-8，8 核 31G，不与任何项目共用），
六个批次全部重跑。

**评测机上还作废过一批。** 2026-09-23 17:15 之前的 `baseline-b` 跑了 13 次，
在检查 q2 的正文时发现 HCA 侧翻遍 `theses/` 只找到 `README.md` ——
**评测账本没有铺进 HCA 工作区**，那道题对 HCA 侧结构性不可能完成

16.1 秒、4 次调用、644 字，看起来又快又干净，其实这道题根本没开始答。

（M2 那次是手工跑的）。现在铺账本放进了 `deploy/eval/i2-up.sh`，每次起栈都做一遍。
作废的那 13 次留在 `docs/eval/i2/_废弃-baseline-b-未铺账本/`。

**同一次起栈还藏着第二个问题，比账本那个更要命。** 把账本铺好之后重跑，
q3 的 HCA 侧仍然是 29 次调用、286 秒、撞满 30 轮上限。翻第一次工具调用的返回才看见：

```
mcp__screener__market_screen → {"detail":"internal auth failed"}
```

6 个 hunter 系 MCP（screener / watchlist / portfolio / hunter_cap / hunter_user / uzi）
都靠 `X-Hunter-Internal-Key` 打基线 api，而评测机 `deploy/.env` 里那把 key 与基线 api
起栈时生成的**不是同一把**。于是每次调用都回这一句，模型换个工具再试 ——
q3 就从「1 次 `market_screen` 搞定」变成在 akshare 里绕 29 次。

**最值得记下来的是它有多安静**：`GET /mcp/status` 全程 `9/9 connected`，
工具全都挂着，daemon 日志一行异常都没有，只有把工具返回的正文翻出来才看得见。

这条已经补进 `deploy/eval/i2-up.sh`：起栈时先比 key 的 md5，再做一次**真调用**的

评测机上跑批次时机器上没有其它负载，每个批次开跑前记 `uptime`、每一次运行记
`loadavg_before` / `loadavg_after`，负载 > 4 就等（`deploy/eval/i2-opt-batches.sh`）。
即便如此，D 维度仍然是**两边中位数相比**的相对打分、A/B 交错且每轮换先手 ——

## 5. fork：三个只在 `config.toml` 里露面的提速参数

用户 2026-09-23 00:55 的指示是「fork 无条件做」，并且「补丁只做提速需要的部分、
全部做成 `config.toml` 里可设置的提速参数、不配置时与上游行为完全一致」。
下面是照这个口径做出来的东西。

### 5.1 三个开关

| 参数 | 位置 | 不配置时 |
|---|---|---|
| `system_prompt`（inline） | `[providers.<name>]` / `[models.<id>]` | 上游**已有这个字段但从来没被读到过**，配了不报错也不生效；补丁把它接上 |
| `system_prompt_file` | 同上 | 新增。整个文件的内容**整体替换**内置编码人设；相对路径按 config 目录解析，inline 优先 |
| `[tools] allow` / `deny` | 顶层 `[tools]` 表（上游已有，此前只有 `todo` 一个子项） | 两个列表都空 = 挂载名单与现在**逐字相同** |

`[tools]` 的模式写法三种：精确名 `read_file`、前缀 `mcp__screener__*`、
族 `group:coding` / `group:codeintel` / `group:atomgit` / `group:skills` /
`group:subagent` / `group:mcp`。`deny` 在 `allow` 之后判，deny 赢。

### 5.2 为什么「挂载过滤」不是「权限规则」

上游已经有 `[permissions] allow/deny`，但它管的是**一次调用要不要弹窗**：
工具照样出现在发给模型的 `tools` 数组里 —— schema 的 token 照付，模型照样会去试，
被拒之后再换一个工具试（这正是 §1.2 量到的「17 407 字节本场景用不上」那部分的代价）。

内核里其实已经有正确的分层。`ToolRegistry::mount` 的注释写得很清楚：

> Unmounted tools never produce a ToolDef and are not resolvable during a turn
> → zero effect on the agent.

缺的只是**让部署方决定挂载名单**的那个口子。所以补丁落在挂载名单上，
注册侧一个字不动 —— 工具照样注册，只是不挂载。

过滤器接在**四个**挂载点上，少一个就是一句空话：

1. 基础工具名单（`prepare_with_plugin_hooks_reusing_lease` 里那份 `names`）
2. MCP 初次就绪时的发布（`publish_ready_mcp_tools`）
3. 单台 MCP 连上时的增量发布（`publish_connected_mcp_server`）
4. 运行时注入的额外工具（`register_extra_tool`，`/loop` 的 `schedule_wakeup` 走那条）

第 2 条尤其要在**记进 `mcp_tool_names` 之前**过滤：那个列表是
`selected_tool_names()` 每次挂载都会重读的，记进去一个没过滤的名字，
下一次发布它就又回来了。

### 5.3 本发行版怎么用

`deploy/daemon/hca-init.py` 在容器启动时渲染 `config.toml`，两项都**只在环境变量
非空时才写进去** —— 所以同一份 compose 既能跑官方二进制、也能跑 fork，
官方二进制上不会躺着一行看起来生效、实际没生效的配置。

```
HCA_LLM_SYSTEM_PROMPT_FILE=/opt/hca/personas/hunter-research.md
HCA_TOOLS_DENY=group:codeintel,group:atomgit,group:subagent,code_review,ast_grep,list_sessions,schedule_wakeup,recall
```

与 llm-shim 那层 `LLM_TOOL_DENY` 的分工：shim 是在**请求出容器之后**把 schema 摘掉，
daemon 侧仍然挂着这些工具；`[tools] deny` 是**根本不挂**。两层都留着 ——
官方二进制上只有 shim 那层可用。
