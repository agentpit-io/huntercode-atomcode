## 0. 一页结论

**同一台机器、同一个 api 进程、同一个 postgres 实例、同一行用户、同一份账本、
同一把模型 key、交错执行每轮换先手** —— 400 次有效运行（10 题 × 两边 × 10 遍
+ A 线 6 遍 + 空载题各 20 遍），结论三句话：

| | **A 线 · 纯引擎**<br>（两边同样 6 个 MCP） | **B 线 · 产品形态**<br>（HCA 10 个 MCP vs 社区版 6 个） |
|---|---|---|
| **空载题**（不调工具）首字中位 | **4.57 s / 4.52 s = 1.01** | 5.35 s / 4.02 s = 1.33 |
| **十题墙钟合计**（中位数之和） | 361.0 s / 302.7 s = **1.19** | **217.9 s / 282.4 s = 0.77** |
| **十题答案首字合计** | 285.5 s / 245.5 s = 1.16 | **164.4 s / 222.9 s = 0.74** |
| 十题首字合计（含「路标」） | 83.4 s / 245.5 s = **0.34** | 103.8 s / 222.9 s = **0.47** |
| 模型段 / 工具段 / 出字段 | 1.08 / 1.23 / 1.72 | 0.94 / **0.45** / 1.52 |
| token 合计 | 587 265 / 651 312 = 0.90 | 660 907 / 672 194 = **0.98** |

1. **引擎本身不慢。** 不调工具、工具清单又拉平的时候，两边首字 **4.57 s vs 4.52 s，
   比值 1.01** —— 这是这一轮里最干净的一个数。
2. **发行形态下 HCA 整体更快，快在工具段。** 十题墙钟 **0.77**、答案首字 **0.74**，
   工具段只有社区版的 **0.45**：不是单次工具更快，是**调得更少**
   （20 次 vs 40 次、27 轮 vs 38 轮），组合工具把 N 次往返压成 1 次。
   **而且 token 打平了（0.98）** —— 这与 I1「HCA 贵 1.34 倍」的结论不同，原因见第 5 点。
3. **把工具清单拉平，优势反过来（1.19）。** 没有组合工具时 HCA 退回 akshare 的
   「search → signature → call」三连，工具段从 54.8 s 涨到 157.4 s。
   这与 I1 A 线量到的 **1.18** 几乎一致 —— 两轮独立复现同一个量。
4. **首字延迟两条线都大幅领先**（0.34 / 0.47）：人设要求先发一行「路标」再调工具，
   社区版倾向「把工具全调完再开口」。**看真正的答案开始出字（答案首字）也领先**
   （B 线 0.74），所以这不只是话术差异。
5. **这一轮最重要的一件事不是数字，是查出并修掉了一个让前几轮口径失真的缺陷**：
   评测账号的 access token 只活 1 小时，导致**社区版那一侧的用户身份从 2026-09-22 17:50
   起一直是断的**（I1 的 60 次社区版运行全部如此）。它不报错，只让 `watchlist_*` /
   `portfolio_*` 读到「没有用户」的数据 —— 社区版于是**不做题就返回**，看着又快又便宜。
   修好之后同一道 `q2`，社区版从 10.6 s 变成 43.5 s（4.1 倍），退回任务的次数从 **8/8**
   降到 **1/10**。**B 线这次的 0.77 与 I1 的 1.057 之差，主要就来自这里。** 详见 §6.1。

**还能不能再快**：能动的只剩 `q3` / `q5` 的**模型段**（+1.5 s / +3.6 s）。
`q5` 的 +3.6 s 与 I3 独立量到的 +3.8 s 对得上（待办池 **P2-23**），
已知的那把杠杆（工具白名单 **U-23**，10.0 ms/千字节）只够补其中约五分之一。
出字段慢 1.52 倍则**不是可优化项** —— HCA 写了 1.74 倍的字，折成每字耗时反而更快。

## 1. 把变量压到只剩引擎 —— 配置证据

### 1.1 同一台机器

专用评测机 **`hca-bench-01`**（8 核 31G、100G 盘，只跑评测，不与任何项目共用，
所有端口只绑 `127.0.0.1`）。两侧栈**同时**在这台机器上跑，
`run_ab.py` 交错执行、**每一轮换先手**（奇数遍 HCA 先、偶数遍社区版先）。

### 1.2 同一个数据库 —— 没走任务书那条退路，因为现状比它更紧一档

任务书给的做法是「基线栈不再起自己的 postgres，改指到 HCA 那套」，
并留了一条退路（两库同构 + 每次恢复同一份 dump，退回时要写明原因、两种口径各一组数）。

**两条都没用上，因为评测拓扑里本来就只有一套后端**：

* HCA 侧只起 `daemon` + `llm-shim`（`deploy/eval/docker-compose.i2.yml`），
  它的 6 个 hunter 系 MCP 通过 `HERMES_API_URL` 打**基线那套 api**
  （`deploy/eval/docker-compose.hca-api.yml`，网络别名 `hunter-api`）；
* 社区版 `opencode` 打的是**同一个容器**（服务名 `api`）；
* 那个 api 只连一个 postgres，而整台机器上**只有这一个 postgres 容器**。

也就是说两边共用的不是「两个同构的库」，是 **同一个 api 进程 + 同一个 postgres 实例 +
同一个库 + 同一行用户**。这比任务书要求的强，所以退路没有被触发，
也就没有「两种口径各一组数」这回事 —— 只有一种口径，而且是更强的那一种。

**每一批开跑前跑一次 `deploy/eval/i4-same-db-proof.sh`，七条判据全绿才开跑**，
输出存进批次目录（`docs/eval/i4/<批次>/same-db-proof.txt`）。判据是：

| # | 判据 | 这一批实测 |
|---|---|---|
| 1 | 整台机器在跑的 postgres 容器只有 1 个 | `hca-baseline-postgres-1`，n=1 ✓ |
| 2 | 两个引擎的 `HERMES_API_URL` 在各自容器里解析出来的 IP **都属于同一个 api 容器** | `hunter-api → 172.18.0.2`、`api → 172.19.0.5`，两个都是 `hca-baseline-api-1` 的 IP（它接了两张网）✓ |
| 3 | 那个 api 的 `DATABASE_URL` 解析出来就是那唯一的 postgres | `postgres → 172.19.0.4` = `hca-baseline-postgres-1`；库名 `hunter`、实例 `system_identifier = 7688402911790690338` ✓ |
| 4 | `users` 表那一行的 id == HCA 的 `HUNTER_USER_ID` == 社区版会话登记表里的 `user_id` | 三个都是 `a080473b-b900-4f43-9154-c204e9a90497`（`users` 表只有 1 行）✓ |
| 5 | **真调用**：两个引擎各打一次 `/api/internal/quant/market_screen` | 两边都 HTTP 200、都命中同样多只（`i4-b` 那批 7 446，`i4-a` 那批 7 449 —— 隔了 6 小时，盘面自己在变，**同一批次内两边一致**才是判据）✓ |
| 6 | 那次调用在**库那一侧**看得见 | 调用前后 `pg_stat_database.xact_commit` 各 +2 ✓ |
| **7** | **社区版走它自己那条身份解析链路**（登录 → 建会话 → 登记 → `GET /api/internal/session/{sid}/user`）**必须解析出同一行用户** | 四个批次都解析出 `a080473b-…` ✓（零 token；负向验证过：故意写错口令 → ✗、`rc=6`、不开跑）|

第 5、6、7 条是这份取证里最要紧的三条：前四条查的都是配置与解析结果，
**这三条查的是行为** —— 事务数涨了才算这次调用真落到了这个实例上，
身份解析得出来才算社区版真读得到这一行用户的数据。

> **第 7 条是这一轮加出来的，因为前六条全绿的那一批后来被作废了** —— 见 §6.1。
> 四个批次的取证原件在 `docs/eval/i4/<批次>/same-db-proof.txt`，**七条全绿**。

### 1.3 同一份数据

* **用户域数据**（自选、持仓、论点、会话归属）在同一个库的同一行用户名下，
  本来就是同一份 —— 但「同一份」不等于「两边都读得到」，这一轮最贵的一课正在这里（§6.1）。
  **行为证据**（2026-09-23 21:59，`docs/evidence/I4/两边看到同一份自选.txt`）：
  同一句「我的自选股里有哪些票？600519 在不在我的自选里？」——

  | 边 | 调的工具 | 工具返回 | 答 |
  |---|---|---|---|
  | HCA | `mcp__watchlist__watchlist_digest` | `total_count:3`、600519/601088/300750、价 1251.24 / 47.21、`avg_pct -0.68` | 「共有 3 只：贵州茅台（600519）、中国神华（601088）、宁德时代（300750）。600519 在你的自选股中。」 |
  | 社区版 | `watchlist_watchlist_digest` | **同一串** —— 三只、同顺序、同价、同 `avg_pct` | 「你的自选股有：贵州茅台（600519）、中国神华（601088）、宁德时代（300750）。600519 在你的自选里。」 |

  两边的工具返回**逐字段相同**（同一个 api、同一行用户），这比任何配置比对都直接。

* **工作区账本**（`holdings/positions.md`、`theses/*.md`）：
  **每一次运行前**把两侧各铺一遍同一份种子（`run_ab.py` 的 `reseed`，
  每次运行的 `reseed_rc` 记在 `index.json` 里）。
  这一步不是洁癖 —— I1 实测社区版在 `q10` 上**真的把账本里的 38.5 改成了 30**，
  不恢复的话下一遍的 `q2` 就会读到被改过的成本价。
* **缓存**：两边共用同一套 api + redis + postgres，缓存状态天然一致。
* **预热**：每批正式开跑前先跑一次 `q1`（空载批次跑 `q0-idle`），**数据丢弃**
  （落在 `<批次>/warmup/`，汇总脚本不读）。

### 1.4 同一模型通道

同一个网关 `hunter.agentpit.io`、**同一把 key**、同一个模型名 `hunter-chat`。
每一次运行前后各查一次网关配额，差值 `quota_delta` 落进记录 ——
报告里每一个 token 数都是这个差值，不是估算。

### 1.5 机器负载

任务书要求「每批开跑前记 `uptime`，负载 > 2 就等」。`i4-batch.sh` 把它做成了闸：
`/proc/loadavg` 的 1 分钟值 > 2.0 就每 60 秒查一次，最多等 30 分钟，等不到就不开跑。

| 批次 | 闸通过时的 1 分钟负载 | 因负载等了多久 | 每次运行开跑前负载（中位 / 最大） | 总耗时 |
|---|---|---|---|---|
| `idle-b` | 0.37 | 0 分钟 | 2.40 / 3.30 | 780 s |
| `i4-b` | 1.03 | **1 分钟** | 1.26 / 2.56 | 9 292 s |
| `idle-a` | 1.87 | 0 分钟 | 1.40 / 2.07 | 720 s |
| `i4-a` | 0.81 | 0 分钟 | 0.44 / 1.35 | 5 677 s |

**要说清楚的一点**：闸只管开跑前。批次一旦跑起来，**评测自己**（docker exec、
探针进程、两个引擎容器）就会把负载抬到 1～3.5，所以「每次运行开跑前负载」那一列
比闸的阈值高是正常的。这个抬升对两边是**对称**的 —— 同一批次里 A/B 交错执行、
每轮换先手，任何一侧都不会系统性地赶上更空或更忙的机器。
I3 §5 记过的那个错误（探针把机器压到负载 6～7 还在计时）这一轮没有重复：
四个批次里每次运行开跑前的负载最大值是 **3.30**。

## 2. 测了什么

### 2.1 四个批次

| 批次 | 题集 | 线 | 每题每边 | 记录数 |
|---|---|---|---|---|
| `idle-b` | `q0-idle`（纯引擎空载题） | 产品形态（HCA 全量 MCP） | 20 | 40 |
| `i4-b` | I1 那 10 道题 | 产品形态 | 10 | 200 |
| `idle-a` | `q0-idle` | A 线（HCA 压成与社区版相同的 6 个 MCP） | 20 | 40 |
| `i4-a` | I1 那 10 道题 | A 线 | 6 | 120 |

任务书要的是「每题每边 ≥ 6 次」与「空载题每边 20 次」，四个批次都达到或超过。
**先跑完两个产品形态的批次，再切 A 线** —— 这样只切两次栈配置，
而「HCA vs 社区版」这个主比较永远是**同一批次内交错**跑出来的。

题面在 `tools/eval/questions.py`，与 I1 逐字相同（`q9` 是 3 轮追问题）。
空载题题面：**「用一句话说明你是什么。不要调用任何工具。」**
两边实测都是 1 轮、0 次工具调用 —— 这是任务书要的「最干净的引擎响应时间对照」。

### 2.2 每一次运行落哪些分段

一次运行切成四段，**HCA 侧四段之和 == 墙钟**（单测钉着，实测残差 < 1 ms）：

| 段 | 定义 | HCA 怎么取 | 社区版怎么取 |
|---|---|---|---|
| **首字延迟 `ttft_ms`** | 消息发出 → 第一块正文到达 | 瀑布里第一个 `text_start` 段的 `end_ms` | 第一个 `stream` 段的 `start_ms` |
| **答案首字 `ttft_answer_ms`** | 消息发出 → **末轮**第一块正文开始 | 同口径 | 同口径 |
| **模型段 `model_ms`** | 不在跑工具、也不在出末轮正文的时间 | `totals.model_ms` | `totals.model_ms` **+ 非末轮的 `stream` 段** |
| **工具段 `tool_ms`** | 全部工具区间的**并集**（并行不重复计） | `totals.tool_ms` | `totals.tool_ms` |
| **出字段 `stream_ms`** | 末轮第一块正文开始 → 最后一块正文结束 | `totals.stream_ms` | 末轮 `stream` 段的 `max(end) − min(start)` |
| **收尾段 `finish_ms`** | 最后一块正文 → 运行结束 | `totals.finish_ms` | **量不到**（阻塞 POST，没有独立的结束事件），写 `null`，上界 = 残差 |
| **hook 段** | 每次工具调用前后内核要等的那段 | 单独直测（§5.3），**不在 SSE 的工具段里** | 社区版**没有 hook 机制**，这一段恒为 0 |

另记：轮数、工具调用次数、正文字数、每字耗时、token（**网关配额差值，不是估算**）、
运行前后的 `loadavg`、账本恢复结果。

**两个首字延迟都给，跨产品比较以「答案首字」为准。** 原因：本部署的人设要求模型在
一批工具调用前先发一行「路标」（「我先查一下 …」），所以 `ttft_ms` 那一块正文
可能是进度提示而不是答案 —— 表里「其中路标」那一列标出了 n 次里有几次是这样。
社区版没有这个行为，它的两个首字恒等。

### 2.3 为什么 hook 段要单独测

I2 §1.1 已经量过并更正过一次：`PreToolUse` / `PostToolUse` 的耗时**不在 SSE 的工具段里**
（pilot 实测工具段 1 157 ms、工具自己报的 `duration_ms` 1 156 ms，差 1 ms），
上游是在发出 `tool_start` **之前**跑 PreToolUse、在 `tool_result` **之后**跑 PostToolUse，
两跳都落进了相邻的**模型段**。所以从瀑布里拆不出来，只能按 hook 真实的调用方式
（payload 从 stdin 进、读 stdout 最后一行 JSON）在容器里直接跑 N 次取中位数。

### 2.4 「原样」与「都真做题」两套数

I1 §3.11 记过：`q2` 上社区版有几次**没做这道题** —— 反过来要用户把论点贴出来
（而 `theses/601088.md` 就在它自己的工作区里）。这种运行又快又短，
混进中位数会让对照组显得很快。所以每道题给两套数：
**原样**（全部有效运行，一次不剔）与**都真做题**（剔掉没做题的）。

判据**与耗时无关**，**逐句判**：一句话里同时出现三件事才算把任务退回给用户 ——
① 祈使（请 / 麻烦 / 烦请）；② 索要动作（提供 / 发给我 / 发出来 / 贴出 / 告知 / …）；
③ 要的是**这道题的材料**（买入理由 / 证伪条件 / 论点 / 逻辑 / 清单 / …）。
另外**空答案也算没做题**。**不作用于 `q4` / `q10`** —— 那两道题的正确答案
本来就可能是「拿不到」「我不做」。

> ⚠ **这条判据在本轮中途改过一次，必须写明。** 原版是全文级的片段匹配，
> 在 I4 的数据上**两头都错**：漏掉了「请**直接将**……发在对话中」（中间插了词），
> 又把 HCA 两次正常作答误判成没做题（`q8`-r10 表格里「尚未提供是否有后续转入
> 引流链路」、`q9`-r2「基本面尚未提供超预期的扩张弹性」，两句都是在描述证据缺口）。
> 改成逐句 + 三件事齐备之后，在**全部 597 次有记录的运行**（I1 的 108 次 +
> I4 四个批次 + 两个作废批次）上逐条打印命中并人工核过：
> **命中 12 次、全部属实、0 误伤**。判据与单测在 `tools/eval/i4_summary.py`
> 与 `tools/tests/test_i4_summary.py`（10 条）。

这 12 次命中的分布本身就是 §6.1 那个缺陷的指纹：

| 批次 | 社区版 `q2` 退回任务的次数 |
|---|---|
| I1（`c1-a` + `c1-b`，各 3 遍） | 3 / 6 |
| I4 `i4-b-作废-token401`（身份断的那批） | **8 / 8** |
| I4 `i4-b`（身份修好之后） | **1 / 10** |

`summary.json` 里每道题都带一个「剔除明细」：剔了哪一次、为什么、
命中的原话是哪一句，不用翻原始记录就能复核。

## 3. 纯引擎空载响应（任务书要的「最干净的一组对照」）

题面：**「用一句话说明你是什么。不要调用任何工具。」**
两边实测都是 **1 轮、0 次工具调用**，所以工具段恒为 0、没有「路标」——
量到的就是「消息进去 → 第一个字出来」这一条链路本身。

### 3.1 三次测量（同一台机器，同一天，间隔 1～3 小时）

| 批次 | 时段（上海） | 线 | 边 | n | 首字中位 | 首字 P90 | 墙钟中位 | token（网关计） |
|---|---|---|---|---|---|---|---|---|
| `idle-b-作废-token401` | 16:47–17:01 | 产品形态 | HCA | 20 | **4.86 s** | 7.12 s | 5.02 s | 22 368 |
| | | | 社区版 | 20 | **4.07 s** | 4.94 s | 4.16 s | 14 825 |

### 3.2 结论

1. **工具清单拉平之后，两边的空载响应时间是一样的：4.57 s vs 4.52 s，比值 1.01。**
   这是这一轮里最干净的一个数 —— **引擎本身不慢**。
2. **产品形态下 HCA 慢 0.8～1.3 s（比值 1.19 / 1.33）**，同时每次请求多花
   约 7 500 token。两件事是同一件事：HCA 多挂的那 14 个工具
   （39 个 vs 25 个）让每一轮请求多带 **10 792 字节**的工具 schema。
3. **但那 0.78 s 不能全算到工具清单头上。** 按 I3 §3 分档实测的斜率
   （工具 schema **10.0 ms/千字节**、提示正文 6.0 ms/千字节，R² 0.99），
   10 792 字节只该值 **约 110 ms**，而实测差了 780 ms。
   剩下的落在**批次漂移**里 —— 同一份配置、同一台机器、隔 20 分钟重测，
   HCA 自己就从 4.86 s 漂到 5.35 s（+10%），社区版从 4.07 漂到 4.02（−1%）。
   这正是待办池 **U-19**「HCA 这种大请求在不同时段拿到的服务质量会漂」的又一次重复。
   **所以这里只下一个能站住的结论：两边空载响应同量级，差值与批次漂移同量级。**

| 系统提示 | 24 254 字符 | 23 294 字符 | +960 |

## 5. 哪一段快、哪一段慢

### 5.1 快在工具段：HCA 的工具时间不到社区版的一半（54.8 s vs 119.9 s）

不是「单次工具更快」，是**调得更少**：十题合计 **20 次 vs 40 次**、**27 轮 vs 38 轮**。
最极端的两道：

* `q1` 基本面：HCA 1 次调用（`hcapack` 组合工具一次拿回快照 + 财务），
  社区版 2 次、工具段 24.97 s vs 3.34 s；
* `q2` 持仓论点复核：HCA 1 次、工具段 3.37 s，社区版 7 次、22.15 s。

这正是 I1 §0 那条「HCA 的优势大部分来自多挂的那几个 MCP」的另一面 ——
**组合工具把 N 次往返压成 1 次，省下来的是往返，不是算力**。

### 5.2 模型段两边基本持平（129.9 s vs 136.5 s = 0.95），但**分布不一样**

HCA 更慢的三道题（`q3` `q5` `q8`），差的**全在模型段**：

| 题 | HCA 墙钟 | 社区版 墙钟 | 差 | 其中模型段差 | 其中出字段差 |
|---|---|---|---|---|---|
| `q3` 因子选股 | 12.39 s | 9.68 s | **+2.71 s** | +1.54 s | +1.05 s（写 1 206 字 vs 796 字） |
| `q5` 情报摘要 | 16.92 s | 11.53 s | **+5.39 s** | +3.59 s | +1.70 s（写 1 698 字 vs 524 字） |
| `q8` 杀猪盘 | 21.75 s | 17.74 s | **+4.01 s** | −0.53 s（HCA 更快） | +2.12 s（写 1 472 字 vs 632 字） |

`q5` 的 **+3.59 s 模型段**正是 I3 记在待办池里的 **P2-23**（I3 量到 +3.84 s）——
**I4 在完全不同的批次、不同的身份配置下重复到了同一个量**，所以它不是噪声。
已知的那把提速杠杆（**U-23** 工具白名单，I3 实测 10.0 ms/千字节 × 30 KB ≈ 347 ms/轮、
两轮约 0.69 s）**只够补上其中的五分之一**，剩下的还没拆开（P2-23 记的做法：
同一道题只改工具返回体积，看首字怎么变）。

### 5.3 出字段慢 1.52 倍，但**每个字更快**

十题合计出字 34.8 s vs 22.9 s，看起来 HCA 慢 —— 但 HCA 写了 **14 122 字**、
社区版 **8 111 字**（1.74 倍）。折成**每字耗时**：10 题里 HCA 有 6 题更快、
2 题持平、2 题略慢（`q10` 1.10、`q4` 1.03）。
**这一段没有可优化的东西，它就是「写得多」的代价**，而写多写少是人设决定的，
不是引擎决定的。

### 5.4 hook 段：每次工具调用要付的那一跳

社区版**没有 hook 机制**，这一段对它不适用（不是 0，是没有这回事）。
HCA 侧的 hook 耗时在 SSE 上和模型调用、MCP 往返混在一段里拆不开（I2 §1.1 已证），
所以**单独直测**：在 daemon 容器里按 hook 真实的调用方式
（payload 从 stdin 进、读 stdout 最后一行 JSON）各跑 11 次取中位数
（2026-09-23 21:5x，栈 `hca-i4`，原始记录 `docs/eval/i4/hook-bench.json`）。

| hook | 事件 | 中位 | 最小 | 最大 |
|---|---|---|---|---|
| `guard` | PreToolUse | 16.4 ms | 16.1 | 16.7 |
| `audit` | PostToolUse | 16.4 ms | 16.2 | 16.7 |
| `context` | UserPromptSubmit | 16.4 ms | 16.1 | 16.6 |
| `lang` | UserPromptSubmit | 16.5 ms | 16.2 | 16.6 |
| `budget` | UserPromptSubmit | 16.4 ms | 16.2 | 17.3 |

* **每次工具调用要付**：`guard` + `audit` = **32.8 ms**；
* **每个提示要付**：三个 UserPromptSubmit hook 上游是并发跑的
  （`cc_hooks.rs:636`），付的是**最大值**不是和 = **16.5 ms**。

五个 hook 的耗时几乎一样（16.4～16.5 ms），说明这一跳的成本**不在脚本逻辑里，
在起进程本身** —— 五个脚本干的事差别很大，耗时却看不出差别。

**折算到这一轮的十道题**：HCA 十题合计 20 次工具调用、10 个提示（`q9` 是 3 轮，
按轮算 12 个），hook 合计 ≈ 20 × 32.8 + 12 × 16.5 = **约 0.85 s**，
占十题墙钟 217.9 s 的 **0.4%**。**这一段不值得优化**，
写在这里是因为任务书要求每一段都要有数，而「小到可以忽略」本身也是一个结论。

> ⚠ 这个 0.85 s 是**推算**（单测的单次成本 × 次数），不是从那 100 次运行里量到的；
> 量不到的原因见 §2.3。`summary.json` 的 `hook` 块里也写明了这一点。

## 6. 本轮查出来的问题

### 6.1 社区版那一侧的用户身份一直是断的 —— 而且从 I1 起就是（已修）

**怎么发现的**：不是开跑前的检查发现的。开跑前那六条同库判据**全绿**，
批次跑到一半我去翻数据，才看见社区版每一次运行记录里的
`claim_status` 都是 **401 `INVALID_TOKEN`**。

**根因**：`eval-account.json` 里存的是建号那一刻拿到的 access token，
而 api 发的 access token **只活 1 小时**（实测 `exp − iat = 3600`）。
评测账号是 2026-09-22 16:50 建的 —— 也就是说**从 17:50 起，
所有批次里社区版的会话归属登记（`POST /api/chat/sessions`）都在失败**。

**为什么六条判据没拦住**：第 4 条查的是 `chat_session_owner` 表里**最近一行**，
而那是更早某次登记成功留下的旧行，跟正在跑的这一批没关系。
判据查了「表里有没有对的行」，没查「这一批有没有写进对的行」。

**后果是静默降级，不是报错**：会话没登记，opencode 镜像里的 `hunter-mcp-context`
插件反查 `GET /api/internal/session/{sid}/user`（`hunter-mcp-context.ts:121`）拿不到人，
`watchlist_*` / `portfolio_*` 照样返回数据，只是那是**没有用户**的数据。
逐条可查的对照：

| 批次 | 社区版 `claim_status` | 社区版 `in_watchlist` true / false | HCA 侧 |
|---|---|---|---|
| I1（`docs/eval/c1/raw/`，60 次社区版运行） | 401 × 60 | — | HCA 侧 19 次 `stock_quickview` **全部 false** |
| I4 `i4-b-作废-token401`（150 次运行） | 401 × 47 | **0 / 27** | **6 / 2**（那 2 次 false 是 002456，它本来就不在自选里，false 是对的） |
| I4 重跑后的 `idle-b` / `i4-b` | **200 × 全部** | 见 §3 / §4 各批次的「社区版身份解析」块 | 同 |

种子账本里那三只票 —— 600519 贵州茅台、601088 中国神华、300750 宁德时代 ——
**都在这个账号的自选里**，解析正常时只要问到它们，`in_watchlist` 就该是 `true`。

**这件事正好打在 I4 的前提上**：I1 的时候两边都瞎，是**对称**的，所以 I1 的分还站得住；
而 I4 一开始把 HCA 的 `HUNTER_USER_ID` 修对之后（见 §6.2），就变成**只有社区版瞎** ——
再比响应时间，比的是「谁读到的数据多」而不是引擎。所以那两个批次作废、重跑。

**修法**（提交 `ca5cc86`）：

1. `eval_opencode.py` 每次运行前用口令文件（建号时写的，与账号文件同目录、600）
   换一把新 token，换不到就退回旧的并告警，结果记进 `token_refresh` 字段。
   **换 token 在计时区间之外**（`t_batch` 在登记之后才起表），不影响已有数据的可比性。
2. 同库判据加**第 7 条**：社区版走它自己那条身份解析链路
   （登录 → 建会话 → 登记 → `GET /api/internal/session/{sid}/user`）必须解析出同一行用户，
   **零 token**。负向验证过：故意把口令写错 → 第 7 条 ✗、脚本 `rc=6`、批次直接不开跑。
3. `i4_summary.py` 每个批次输出一个「社区版身份解析」块（登记成功率、
   `in_watchlist` 命中数），**有一次失败就判这批不可用**；4 条单测钉住。

**作废的数据原样留档**在 `docs/eval/i4/i4-b-作废-token401/` 与
`docs/eval/i4/idle-b-作废-token401/`（去掉 `.sse` 省体积，`claim_status` 逐条可查）。

**对 I1 结论的影响**：I1 两边对称地读不到用户域数据，所以**四维分仍然成立**，
但要加一条口径注记 —— I1 量的是「两边都没有用户上下文」时的表现。
已写进 `docs/开发文档/待办池.md`。

### 6.2 评测机上四份 `deploy/.env` 里的 `HUNTER_USER_ID` 都不是这套库里的用户（已修）

开工时就发现的（提交 `0406ddf`）：评测机上的 `deploy/.env` 是从测试机拷来的，
里面的 `HUNTER_USER_ID` 是**测试机那套库**的用户 id，这套评测库里根本没有那一行。
后果同样是静默的 —— 按用户取数的 MCP 返回空数据，而 `mcp/status` 照样报 connected。
修法是在 `i2-up.sh` 里加一道闸：起栈时核对 `HUNTER_USER_ID` 与评测账号对不对得上，
对不上直接不起栈。

## 7. 结论与下一步

### 7.1 回答任务书的四个问题

| 问题 | 答案 |
|---|---|
| **哪一段快** | **工具段**。B 线十题 54.8 s vs 119.9 s（0.45）。不是单次更快，是调得更少（20 次 vs 40 次、27 轮 vs 38 轮），组合工具把 N 次往返压成 1 次 |
| **哪一段慢** | **出字段**（1.52）和 `q3` / `q5` 的**模型段**。出字段慢是因为写了 1.74 倍的字，折成每字耗时 HCA 反而更快，**不是可优化项** |

| **还能不能动** | **能动的不多**。已知杠杆 U-23（工具白名单，10.0 ms/千字节）在 `q5` 上只够补约 0.69 s / 3.59 s；剩下的没拆开，做法见待办池 P2-23 |

### 7.2 这一轮的数能拿去做什么、不能做什么

**能**：

* 同一批次内两边的相对关系（比值、倍数）—— 这是唯一严格成立的口径；
* 「引擎本身不慢，差异来自工具清单与出字量」这个结论 —— A 线 / B 线 / 空载题
  三组数互相印证，且 A 线的 1.19 与 I1 的 1.18 在两轮独立评测里重复到了。

**不能**：

* **不能跨轮和 I1 / I2 / I3 的绝对值相减**。理由有两条：① 待办池 U-19 那条 ——
  同一份配置隔一夜就能漂（本轮内部也重复到了：同一份配置隔 20 分钟，
  HCA 空载首字从 4.86 s 漂到 5.35 s）；② **更要紧的是口径变了** ——
  I1 那一轮社区版没有用户身份（§6.1），它的绝对值本身偏快。
* **不能当能力评分用**。这一轮不打四维分，只量时间；题目的对错口径仍以 I1 为准。
* `q4` 的 B 线数字两边做的不是同一件事（HCA 真跑 Kronos GPU 推理、社区版如实说没有），
  报告里凡引用合计都同时给了「去掉 q4」的版本。
