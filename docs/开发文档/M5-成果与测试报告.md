## 2. 偏离计划的决策与原因

| # | 决策 | 原因 |
|---|---|---|
| D-1 | **工具名叫 `upstream_diff.sh` 而不是计划里的 `sync_upstream.sh`** | 总控已拍板决策 2 明确「**不做持续同步**、不写同步脚本」。这个脚本只出**差异报告**，一行代码都不改、一个文件都不同步 —— 叫 `sync_` 会误导使用者以为它会动仓库 |
| D-2 | **差异工具只比四个外部面，不比整仓** | 上游一次发布动几万行（5.0.9 → 5.1.0 之间）。直接 `git diff` 的输出没人会看完，看完也答不出「我们依赖的接口有没有变」这个唯一要紧的问题 |
| D-3 | **P0-11 的绕法做成「裁成合法 JSON + 明确说明」，而不只是「裁小」** | 内核那种「头 4 KB + 尾 4 KB」的砍法留下的是**断裂的 JSON**，模型看不出自己少了什么，才会拿记忆去补（M2 实测过后果）。我们裁完必须让模型**知道少了多少、为什么少、怎么拿全** —— 这才是这条修复的实质 |
| D-4 | **P1-19 用源码级证明代替原计划的故障注入** | 原计划是「用故障注入造一次真事件」。真去读源码才发现这两个事件在本发行版的配置下**结构上发不出来**（对应的工具都被 env 关了），造不出来；而对着请求结构体核应答体反而查出了两处真错。证明比注入强 |
| D-5 | **出口语言守卫落在 BFF 而不是 hook** | AtomCode 的 8 个 hook 事件里没有「助手正文写完」这个点（`Stop` 拿不到正文）。BFF 本来就坐在 SSE 流上，手里有每个文本 part 的终态 —— 这是唯一的落点 |
| D-6 | **P0-10 加的是「事后行为判定」，不是「事前拦截」** | 事前拦截需要知道 runtime 当前的工具清单，而 `/live` 的 snapshot 里没有（已请上游补，questions B12）。事后从工具序列能认出失效的形状，虽然救不回当时那一轮，但能把它变成一条**看得见的日志**并让下一轮恢复 —— 从"完全没有观测手段"到"有一条日志"，这个差别是实的 |

| D-8 | **U-9（M2 剩下 7 次 A/B 评测）本轮没做** | 不在任务书范围内，而且跑 7 次评测会和浸泡抢这台 2 核机器。仍挂在「需要用户决定」 |
| D-10 | **做了任务书里没有的两件事：Ollama 通道实测、`tools/e2e/run.sh`** | 两件都不是「顺手加功能」，而是**把已经写在文档里的承诺兑现**：安装向导首页摆着「三选一」而第三条从没在真机上跑过（M4 给的「磁盘紧张」这个理由已经不成立）；开发者指南从 M4 起就写着一条根本不存在的命令。发现时离「本轮能做完」只差一两个小时，不做就是**留着一句假话发版**。结果证明值得：Ollama 一测就是三个真缺陷，还连带撞出每日探活是假绿（§3.12） |

### 3.2 `tools/upstream_diff.sh`（任务书第 2 条）

**它做什么**：把 AtomCode 两个版本的源码各抽出一份「四个外部面的事实清单」，再逐行 diff。

| 面 | 抽什么 |
|---|---|
| 1 · daemon 路由与 SSE 事件 | `.route()` 的路径与方法动词（按配对括号取参数，不会串到下一条）；`LiveWireEvent` 的 28 个 `type` 取值与每个变体的载荷字段 |
| 2 · skill 解析 | `struct Skill` / `struct Frontmatter` 的字段与 serde 属性、目录与文件名字面量、`GET /skills` 的回包形状（`SkillInfo` 字段 + `get_skills` 里赋了哪几个） |
| 3 · hook | `HookEvent` 枚举、`cc_name()` 返回值、`from_str` 接受的写法、`.hooks.json` 相关字面量、输入输出 JSON 键 |
| 4 · MCP 配置 | `mcp/config.rs` 的结构体与枚举（带 serde rename）、`.mcp.json` 的键、信任门常量、超时常量 |

**为什么不是 `git diff`**：5.0.9 → 5.1.0 之间上游动了几万行，直接 diff 回答不了
「我们依赖的接口有没有变」。

**最要紧的设计**：抽不到就写 `!! 抽取失败` 并让 `rc=3`。
**抽漏了报「无变化」是最危险的假阴性** —— 升级方看到一片绿就换底座。
`tools/tests/test_upstream_diff.py` 里 15 条测试钉抽取器的行为，
其中每个面都有一条「读不到源码 / 找不到枚举时必须报失败」的用例。

写的过程中被自己的测试抓到过一个真 bug：顶层逗号切分没把泛型算进去，
`stats: HashMap<String, u64>` 会被切成两半、后半截匹配不上字段正则**被静默丢掉** ——
正是最危险的那种假阴性。已修并补测试。

**实跑结果**（报告在 `docs/upstream-diff/`）：

| 对比 | 面 1 路由/SSE | 面 2 skill | 面 3 hook | 面 4 MCP | fork 补丁 |
|---|---|---|---|---|---|
| **5.0.9 → 5.1.0** | **3 行**（净增 1 条路由 `GET /projects/:hash/sessions/:id/transcript`） | 无变化 | 无变化 | 无变化 | ✅ 能打上（18 个文件） |
| 5.1.0 → 5.0.9（默认调用形态，从 pins.lock 当前版本出发） | 3 行（反向） | 无变化 | 无变化 | 无变化 | ✅ 能打上（17 个文件） |
| 5.0.8 → 5.0.9（额外验证「它能不能真的看出变化」） | **5 行**（净增 3 条路由：`/codingplan/usage/daily`、`/codingplan/usage/summary`、`/fs/search`） | 无变化 | 无变化 | **1 行**（`McpConfigSource` 多了 `Driver`） | ✅ 能打上 |

**结论有意义**：三版之间 skill 解析与 hook 事件格式**一处没变**，
MCP 配置只多了一个枚举值，daemon 路由是净增 —— 经验上兼容性很好。
但上游没有书面承诺，这正是 questions B6 要问的。

**为什么比的是 5.0.9 ↔ 5.1.0**：任务书要求「v5.1.0 与上游**最近一个更早的发布**」。
收尾时（2026-09-22 19:55）又查了一次 npm registry —— `npm view @atomgit.com/atomcode versions`
最新的一组仍是 `5.1.0`（及其 6 个平台包），**5.1.0 之后上游没有发新版**，
所以 5.0.9 就是「最近一个更早的发布」，这一对是对的。

**顺带查出 E1**（新问题）：release tag 上的 `latest.json` 写的是上一版。
脚本因此改成按文件内容回溯同步 commit，不读 tag 上的文件。

**但真正该记的是：拿这个工具自己做对抗性测试，它当场就假阴性了一次。**

这个工具的全部价值在于「报无变化时可以信」。所以不能只测「有变化时能不能看出来」，
得测「**该失败的时候会不会假装成功**」。做法：把 v5.1.0 的源码解出来，
模拟上游一次重构 —— 把 `pub enum HookEvent` 改名成 `HookEventKind` —— 再抽一遍。

结果：**抽取器照样抽出 8 个变体，报告写「hook 面无变化」**。换底座的人看到一片绿就换了。

两个根因都在 `brace_block()`：① 正则 `enum\s+HookEvent\s*` 匹配上了
`enum HookEventKind` 的**前缀**，然后 `find("{")` 跨过 `Kind` 找到后面的花括号；
② `find("{", …)` 本来就能跨几百行抓到一个毫不相干的块（比如声明其实是
`type HookEvent = …;`）。加了两道闸（匹配末尾不许切在标识符中间、
`{` 必须紧跟声明头）之后复验：

| 对抗用例 | 加固前 | 加固后 |
|---|---|---|
| `enum HookEvent` → `HookEventKind` | ❌ 报「无变化」 | **rc=3，`!! 抽取失败: hook —— 找不到 enum HookEvent`** |
| `enum LiveWireEvent` → `LiveWireEventV2` | ❌ 报「无变化」 | **rc=3，如实报失败** |
| `struct Skill` → `SkillDef` | 作为 diff 行可见 | 同左（这类是「条目」不是「容器」，本来就该由 diff 体现） |
| `struct McpServerConfig` / `enum McpConfigSource` 改名 | 作为 diff 行可见 | 同左 |

加固过程中**自己又坏了一次**：新闸把 SSE 载荷那处也拦住了
（它故意用宽松正则扫 item 原文，会先匹配到文档注释里的大写词
`/// Persistence warning:`），结果三个变体的载荷字段变成「(无字段)」——
又是一次静默丢字段。改成在去掉注释/属性的正文上按变体名精确匹配。

**行为保持的证据**：加固后对真 v5.1.0 重抽，四个面的事实清单与加固前**逐字一致**；
两组正式差异报告重跑，除时间戳与临时目录路径外无变化。
测试从 15 条加到 18 条。

**可复现性也当场核过一次**（2026-09-22 16:24，开发机）：
`tools/upstream_diff.sh --from v5.0.9 --to v5.1.0` 重跑一遍，
与仓库里那份 `docs/upstream-diff/5.0.9__5.1.0.md` 逐行 diff ——
**只差两行：生成时间戳与临时工作树路径**（`/tmp/hca-upstream-diff.XXXX/`）。
结论（面 1 变 3 行、面 2/3/4 无变化、fork 补丁 18 个文件能打上）逐字相同，rc=0。

### 3.3 P0-11：MCP 返回的大小闸

**修复前的实测**（`docs/evidence/M5/p0-11-修复前-容器实测.txt`，零 token）：
部署中的 v0.1.0 容器里，`akshare_call` 对一张 50 行 × 84 列的财务宽表返回
**206 832 字节 = 内核阈值的 12.6 倍**，而返回里的 `truncated` 是 `None` ——
因为 50 行没超过 `AKSHARE_MAX_ROWS=50`，**server 自己认为它给全了**。
这说明 P0-11 原本设想的绕法（「加行数上限」）对宽表**完全无效**。

**做了什么**：

1. `akshare_call` 加**字节预算**（`AKSHARE_MAX_BYTES`，默认 15000，给内核的 16384 留余量）
   与**列投影**（新参数 `columns`）。先按行数限，再二分把行数压到字节预算以内。
2. 6 个 hunter 系薄代理统一走 `tools/opencode-mcp/hca_size_guard.py`：
   超预算时按最大的那个列表字段二分裁，补一个 `_hca_size_guard` 块，
   明说「共 M 条、这里只给了 N 条、**剩下的是被裁掉的不是不存在**」。
   **裁完永远是合法 JSON** —— 这是与内核那种砍法的本质区别。
3. `.atomcode.md` 第五节新增第 8 条：三种截断（我们裁的 / 内核裁的 / 任何情况）
   各自怎么处理，以及「被裁掉那段里的数字不许出现在回答里，更不许标上工具来源」。

**然后把这道闸自己当被测对象查了一遍，又查出三处真缺陷** —— 三处都是
「修复本身在某一档上等于没做」，而且**只有真去量字节数才看得见**：

| # | 缺陷 | 实测 | 根因 |
|---|---|---|---|
| ① | `hca_size_guard.fit()` 的**第 3 档**（单条就超预算 / 非结构化文本）按**原始**字节截，再整个 `json.dumps` | 一条 36 023 字节、内容是 `"\` 重复的记录 → 输出 **29 245 字节**，不但超 15 000 的预算，**还超过内核 16 384 的阈值** | JSON 转义会膨胀（`"`→`\"`、`\`→`\\`），一段全是这两个字符的内容进 JSON 后体积翻倍。改成对**最终输出**二分 |
| ② | `akshare_call` 的行数二分压不住**长文本单元格** | 公告/研报/新闻正文那类接口，容器实测 `stock_notice_report` 形状的**单行**返回 **90 168 字节**（内核阈值的 5.5 倍）；多行长文本二分到 1 行仍有 24 414 字节 | 行数砍到 1 就没得砍了。补第三道闸：**裁单元格**，裁过的在末尾标原长度并出 `cells_truncated` |

### 3.7b guard hook：bash 判据从 denylist 改成 allowlist（本轮最大的一处安全改动）

**不在任务书里，是复核 M4 那四条绕过时顺手多问了一句问出来的**：M4 堵的是
*内联*命令（后台 shell、直接 `import akshare`、`env`/`timeout`/`sh -c` 包装、
带 `..` 的越界路径）。那 —— **脚本不写在命令行里呢？**

#### 第一轮：5 条

`DATA_LIB_RE` / `INLINE_NET_RE` / `INLINE_WRITE_RE` 判的都是**命令行文本**。
脚本在文件里、或从管道进来时，正则什么也看不见。实测全部放行：

```
放行  python3 reports/x.py
放行  sh notes/x.sh
放行  cat notes/x.py | python3
放行  echo <base64> | base64 -d | sh
放行  echo <base64> | base64 -d | python3
```

而 `write_file` 本来就允许往 `reports/` 与 `theses/` 写（有单测钉着）。
**两步接起来就是完整绕过**：

1. `write_file reports/fetch.py`，内容 `import akshare; …` → 允许
2. `bash python3 reports/fetch.py` → **放行**

后果与 M3 §5 那次真浏览器拍到的一模一样：取到的数不进 MCP 层，
拿不到 `_hermes_user_id`、不进审计、富卡片退化成通用卡。

#### 第二轮：照同一条思路继续找，又 7 条

```
放行  find reports -name '*.py' -exec python3 {} ;
放行  awk 'BEGIN{system("python3 reports/x.py")}'
放行  . reports/x.sh              放行  source reports/x.sh
放行  eval "$(cat reports/x.sh)"  放行  perl -e 'system("…")'
放行  node reports/x.js           放行  ./reports/x.py
```

**这 12 条彼此毫无关系。** 问题不在「这次漏了几条」，
而在 denylist **永远只覆盖已经想到的那些** —— 而漏网一条就是完整绕过。

#### 所以改成白名单

`BASH_ALLOW` 只收**不会写文件、不会联网、不会执行外部代码**的东西
（`ls` / `cat` / `head` / `grep` / `find` / `wc` / `sort` / `jq` / `echo` / `date` …）。
刻意不收：`awk` / `perl` / `node` / `ruby` / `php` / `Rscript`（都能 `system()` 出去）、
`sed`（GNU 的 `e` 标志能执行命令、`w` 能写文件）、`tar` / `zip`（能写）、
`eval` / `source` / `.`、`tee`。解释器（`sh` 族与 `python` 族）另有更严的判据：
**只许 `-c` 内联 / `-m` 模块 / 问版本**，其余一律拒，
包括**光秃秃一个解释器**（那就是在从管道读）。`find` 的 `-exec` 一族单独拦。

**换白名单的代价不是猜的，是量出来的** —— 翻部署中容器里的
`/workspace/.atomcode/guard.jsonl`（真实会话记录），模型发出的 **37 次 bash**：

> 原先写「29 次是 `python3 -c` 调 akshare（本来就该拦），其余只有 echo / env / curl」。
> 真去逐条读命令原文才发现：调 akshare 的只有 **4** 次；**29 是旧 guard 判 `proceed` 的条数**，
> 两件事被写混了。下面是逐条读原文之后的真实分布。

| 次数 | 意图 | 该不该拦 |

| **20** | `python3 -c` 内联读文件 / 解析 JSON / 算数 | **正当**（白名单放行 `-c` 内联） |
| 4 | `python3 -c "import akshare as ak …"` 直接调取数库 | 该拦 |
| 4 | `/opt/hca/venv-hunter/bin/python -c "sys.path.insert('/opt/hca/mcp') …"` 直接跑 MCP 源码 | 该拦 |
| 3 | `python3 -c` 里自己 `urllib` 发 HTTP | 该拦 |
| 3 | `echo hello` | **正当**，白名单里 |

**正当用途 25 / 37**，其中最大的一类是「用 `python3 -c` 读文件、解析 JSON、算数」——
而白名单本来就放行 `-c` 内联代码（只禁跑脚本文件与从管道读），所以它们照样能用。
研究工作区的 bash 本来就只该用来做只读查看：取数调 MCP 工具、计算用 `python3 -c`、
留档用 `write_file`。

### 3.7c guard hook：白名单里的「只读工具」自己会写文件、会执行命令

**把 3.7b 那道刚改好的白名单自己当被测对象，又找出 4 条。**
这一条和 3.7b 是同一个错的两面：3.7b 解决的是「首词是谁」，
可白名单里的命令**自己会不会写文件**，它管不着 —— 而写重定向那道闸只认 `>` 和 `>>`。

```
放行  sort -o holdings/positions.json reports/evil.txt
放行  sort reports/a.txt --output=holdings/positions.json
放行  uniq reports/evil.txt holdings/positions.json      ← 第二个操作数就是输出文件
放行  xxd -r reports/p.hex holdings/positions.bin
```

**不是纸面推演，两头都量了**：

* 部署中的 daemon 容器里 `command -v` 逐个查，**`sort` 与 `uniq` 都在**
  （`xxd` / `tree` / `yq` / `jq` 不在，但它们在 `BASH_ALLOW` 里，换个基础镜像就会有）；
* 开发机上直接跑命令，`sort -o` 与 `uniq 输入 输出` **真的把 `holdings/positions.json`
  整个覆盖成了 `TAMPERED`**。后果与 M2 冒烟题「改我的持仓文件」要求拒绝的是同一件事。

判据按两种形式补：**输出文件是选项值**（`sort -o` / `tree -o` / `yq -i`）、
**第二个操作数就是输出文件**（`uniq` / `xxd`）。后者必须先知道哪些短选项吃掉一个值，
否则 `xxd -l 100 a.bin` 会把 `a.bin` 当成"输出文件"而误伤 —— 反误伤用例里专门钉了这一条。

两类各自复验：写盘 **17 条（6 该拦 / 11 该放）**、执行 **7 条（4 该拦 / 3 该放）**，
**0 条不符合预期**；既有 33 条 guard 单测与 3.7b 那 12 条绕过用例一条没红；新增 4 条单测
（`tools/tests` 从 202 → **206 passed, 1 skipped**）。前后对照与容器里的 `command -v` 原文在
[`docs/evidence/M5/guard-输出文件参数绕过-实测.txt`](../evidence/M5/guard-输出文件参数绕过-实测.txt)。

**所以修完之后没有停在"补上这几条"**，而是把 `BASH_ALLOW` 里 62 个命令
按「能不能写文件 / 能不能联网 / 能不能执行外部代码」三问逐个过了一遍
man / `--help`（脚本扫可疑关键词 + 可疑项人工看），**于是又查出第二类**：

```
$ echo 'print("PWNED-BY-RG-PRE")' > x.py
$ rg --pre python3 --pre-glob '*.py' 'PWNED' .
./x.py:PWNED-BY-RG-PRE      ← 这一行不是搜到的内容，是 python3 x.py 的执行输出
```

`rg --pre CMD` 会把每个输入文件先交给 `CMD` 跑一遍再搜它的 stdout ——
「先 `write_file reports/fetch.py` 再执行它」那条绕过原样复活。
容器里没装 `rg` 也没装 `ack`（`command -v` 查过），**当前不可利用**，
但白名单随工作区模板走，换个基础镜像就有了：`rg` 的
`--pre` / `--pre-glob` / `--hostname-bin` 一律拒，`ack` 直接移出白名单。

这一轮也**核实了一批假阳性并且没有动它们**（都是"输出格式/分隔符"而不是"输出文件"）：
`column --output-separator`、`comm --output-delimiter`、`cut --output-delimiter`、
`df --output=字段表`、`join -o 格式`、`ls -o`、`od -o`、`strings -o`、
`find -o`（即 `-or`）。逐条记在证据文件第 7 节。

**方法论上值得记一句**：3.7b 的结论是"denylist 永远只覆盖已经想到的那些"，
所以换成了白名单。这两条说明**白名单也不是终点** —— 它换掉的是
"有没有想到这个命令"，换不掉"有没有想清楚这个命令能干什么"。
白名单的正确用法是：进名单要付一次审查成本，而不是看着眼熟就放进去。

### 3.7e 拿 37 条**真实** bash 重放白名单：撞出两个误伤，也撞出自己写错的一个数

3.7b 那张「换白名单的代价」表是**读着记录估的**，这一轮决定把它重放一遍 ——
把容器 `guard.jsonl` 里模型真实发出的 37 条 bash 原样喂给新 guard。结果三件事：

**① 3.7b 那张表自己是错的。** 原先写「29 次是 `python3 -c` 调 akshare」。
逐条读命令原文：调 akshare 的只有 **4** 次，`/opt/hca` 下跑 MCP 源码 4 次、
内联发 HTTP 3 次、curl 1 次 —— 该拦的一共 12 条；剩下 **25 条是正当用途**，
其中 20 条是「`python3 -c` 读文件 / 解析 JSON / 算数」。
**29 其实是「旧 guard 判 proceed 的条数」**，被我写成了「调 akshare 的次数」。
这个错会让人以为白名单几乎没有代价（"正当用途只有 echo 与 env"），
而真实情况是正当用途占了三分之二 —— 结论仍然成立（那 20 条白名单照样放行），
但**得出结论的证据是假的**，所以必须改。

**② 误伤一：`open(..., 'r')` 被当成写文件。**

```python
INLINE_WRITE_RE = ...  open\s*\(\s*[^)]*['"][waxr]\+?['"]     # ← `\+?` 是可选的
```

`[waxr]` 里的 **`r`** 加上可选的 `+`，等于把**只读**的 `'r'` 也算成写。
重放时两条正当的只读用法被拦：

```
python3 -c "with open('.eval/x.sse', 'r', errors='ignore') as f: ..."
python3 -c "with open('.atomcode/skills/deep_analysis/SKILL.md','r') as f: print(...)"
```

「用 `python3 -c` 读文件算数」正是白名单刻意要放行的用法，拦掉它等于把 bash 废掉一半。
判据改成「只有 `w`/`a`/`x`（可带 `b`/`t`/`+`）和 **`r` 带 `+`** 才是写」，
16 个模式逐个验过（`'r'`/`'rb'`/`'rt'` 放行，`'r+'`/`'r+b'`/`'w'`/`'wb'`/`'a+'`/`'x'`/`'w+'` 拦）。

**③ 误伤二：`2>/dev/null` 被当成写盘。** 写重定向那道闸只看 `>`，

`tools/tests` 从 206 → **208 passed, 1 skipped**。

**④ 顺带还有一个同类的**：等待测试机安静下来的脚本用
`pgrep -f 'cargo|rustc'` 判「对方的 cargo 跑完没有」，
而 `-f` 匹配**整条命令行** —— 它撞上了上一轮自己留下的等待壳
（`bash -c 'until ! pgrep -f "cargo clippy" …'`），于是恒返回 4、**永远等不到安静**。
真实的 `cargo`/`rustc` 进程数是 0。改成按**进程名**匹配（`pgrep -x`）。
和 §3.3 那条「测试写了从来没跑过」是同一个形状：**判据自己坏了，而表面一切正常。**
