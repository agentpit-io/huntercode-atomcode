# 部署与运维手册

> 面向**私募机构的 IT / 运维**。前提：你有一台 Linux 服务器的 root 或 sudo，
> 会用 docker，不需要懂 Python / Rust / 前端。
>
> 这套东西的定位：**一台机器上的投研助手**。行情、持仓、研究结论、对话记录全部落在
> 这台机器的磁盘上；唯一出网的是大模型调用（可以换成本地 Ollama 做到完全离网）。

## 0. 三分钟版

```bash
# 1) 下载安装脚本（GitHub / GitCode 二选一）
curl -fsSLO https://raw.githubusercontent.com/agentpit-io/huntercode-atomcode/main/deploy/install.sh
# 2) 装
bash install.sh
# 3) 装完屏幕上会打印访问地址与管理员口令文件位置
```

交互里只有六个问题：装到哪 → 模型通道（默认第 1 个）→ 网关地址 → API key
→ 数据接口 key → Kronos key。**后两把与模型通道分开计量**，都可以直接回车跳过；
跳过时脚本会明确告诉你会少哪块功能（truesource 类工具、Kronos 预测与回测看板），
而不是装完之后让你自己去猜为什么没数。
装完自检不过**脚本会失败退出**，不会给你一个"起来了但用不了"的栈。

无人值守：

```bash
bash install.sh --non-interactive --yes \
  --dir /opt/hca \
  --channel oneapi \
  --api-key-file /root/hca-key \
  --data-key-file /root/hca-data-key \     # 可选：truesource / 行情增强
  --kronos-key-file /root/hca-kronos-key \ # 可选：K 线预测与回测看板
  --web-port 3200 \
  --admin-email it@yourfund.com
```

> 三把 key 申请入口都是 <https://hunter.agentpit.io/dev/api-keys>。
> 装完之后想补，改 `deploy/.env` 里的 `HUNTER_API_KEY` / `KRONOS_API_KEY`
> 再 `bash deploy/up.sh --no-build` 即可（0.1.1 之前只有这一条路，
> 因为安装脚本压根不问这两把 key —— 见 M5 报告 R-22）。

## 1. 硬件与系统要求

| 项 | 最低 | 建议 | 说明 |
|---|---|---|---|
| CPU | 2 核 | 4 核 | 2 核能跑；`next build` 那一步慢（实测约 5.5 分钟） |
| 内存 | 4 G | 8 G | **构建 web 镜像最吃内存**，4G 以下大概率 OOM。可以在别的机器上构建好镜像再 `--no-build` |
| 磁盘 | 20 G | 50 G+ | 镜像与依赖约 8～12 G；postgres 数据与对话记录另算 |
| 系统 | Ubuntu 22.04 / Debian 12 / 任何带 Docker 的 Linux | Ubuntu 24.04 | 实测机是 Ubuntu 24.04 · 2 核 8G |
| Docker | Engine 24+ 且 **compose v2** | 最新 | `docker compose version` 能出版本号就行；旧的 `docker-compose`(v1) 不支持 |
| 出网 | 拉镜像 + 模型 API | — | 国内网络见 §7；完全离网见 §8 |

macOS：脚本做了适配（Ollama 用 `host.docker.internal`、会提示 Docker Desktop 的内存设置），
但**没有在真机上测过**，见 `docs/开发文档/M4-成果与测试报告.md`。Windows 未适配。

## 2. 装出来的是什么

六个容器，一个 compose 项目（默认项目名 `hca`）：

| 服务 | 镜像 | 宿主端口 | 干什么 |
|---|---|---|---|
| `web` | 本机构建 `hca-web` | **3200（唯一对外）** | Next.js 终端 + BFF 转发层（AtomCode 适配就在这一层） |
| `api` | 公开 GHCR `hunter-community-api:1.2.0` | 8200，**只绑 127.0.0.1** | 用户 / 自选 / 组合 / 回测 / 额度；6 个 MCP 反调它 |
| `daemon` | 本机构建 `hca-daemon`（内含 AtomCode 官方二进制 v5.1.0） | **不发布** | 对话内核；9 个 MCP 都是它的子进程 |
| `llm-shim` | 本机构建 `hca-llm-shim` | **不发布** | OpenAI 协议兜底修补（并行 `tool_calls` 缺 `index`） |
| `postgres` | `postgres:16-alpine` | **不发布** | 业务库 |
| `redis` | `redis:7-alpine` | **不发布** | 缓存与队列 |

数据卷（`docker volume ls | grep hca`）：

| 卷 | 装什么 | 能不能删 |
|---|---|---|
| `hca_workspace` | **研究工作区**：`holdings/` 持仓、`theses/` 投资论点、`factors/` 因子、`reports/` 报告、审计日志 | ❌ 这是用户资产 |
| `hca_atomcode-home` | 会话记录（`sessions/*.jsonl` + `.meta`）、`config.toml` | ❌ 删了历史对话就没了 |
| `hca_pgdata` | postgres 数据 | ❌ |
| `hca_redisdata` | redis 持久化 | ⚠️ 只有缓存，删了会重建 |
| `hca_daemon-token` | daemon 自己生成的访问 token | ✅ 重启会重新生成 |

**`deploy/up.sh --down` 只删容器、不动卷。** 想彻底清掉数据要显式
`docker compose -p hca down -v`（会删上面全部卷，**没有二次确认**）。

## 3. 装完先核对这几项

```bash
cd <安装目录>
bash deploy/up.sh --status
```

应该看到（数字都是真查出来的，不是写死的）：

```
  GET /health   : {"status":"ok","version":"5.1.0",…}
  GET /skills   : 6 个： …
  GET /mcp/status: 9/9 connected，工具 28 个，trusted=True，blocked=[]
  api /api/health: {"status":"ok"}
  api 注册策略   : single_user=False registration_mode=invite
  web 首页       : HTTP 200
  web→daemon     : model=hunter-chat
```

任何一项打 `—` 就是**没装好**，别当成正常：

| 症状 | 最常见的原因 |
|---|---|
| `web→daemon : —` | web 读不到 daemon 的 token（权限）或内网不通。M3 踩过：容器 healthy 但适配层全废 |
| `/mcp/status` 少于 9 | 某个 MCP 起不来。`docker exec hca-daemon python3 /opt/hca/tools/dump_mcp_tools.py` 看每个 server 的报错原文 |
| 网页能开、发消息没回答 | 模型 key 无效 / 通道地址错。`docker logs hca-daemon | tail -50` |
| `6 个 hunter 系 MCP 调用报连不上` | `api` 没起来或 `HUNTER_INTERNAL_KEY` 两边不一致 |

## 4. 日常运维

### 4.1 常用命令

```bash
cd <安装目录>
bash deploy/up.sh                 # 重新拉起（**可重复执行**，已经健康就只是核对）
bash deploy/up.sh --status        # 状态 + 自检
bash deploy/up.sh --down          # 停（保留数据卷）
bash deploy/up.sh --no-build      # 不构建，只启动
bash deploy/up.sh --rebuild       # 不用缓存重建镜像
bash deploy/up.sh --admin         # 重新创建/重置管理员账号
docker compose -p hca logs -f daemon      # 跟日志
```

### 4.2 升级与回滚

```bash
bash deploy/install.sh --upgrade              # 升到最新 tag
bash deploy/install.sh --upgrade --ref v0.1.1 # 升到指定版本
bash deploy/install.sh --rollback             # 回到上一次升级前
```

* 升级 = 换代码 + 重建镜像 + 重新拉起，**数据卷一律不动**；
* 升级前自动存回滚点（当时的 commit + 当时的 `deploy/.env`）；
* 自检不过会明确告诉你回滚命令，而不是留一个半死的栈；
* ⚠️ **回滚只回代码与镜像，数据库结构留在新版**。本项目的迁移都是加表加列，
  旧代码照样跑；哪天出现破坏性迁移，会在那个版本的发布说明里写明。

### 4.3 备份

要备份的是三个卷 + 两个文件：

```bash
# 停机备份（最稳）
cd <安装目录> && bash deploy/up.sh --down
for v in workspace atomcode-home pgdata; do
  docker run --rm -v hca_$v:/src -v "$PWD/backup:/dst" alpine \
    tar czf /dst/$v-$(date +%F).tgz -C /src .
done
cp deploy/.env backup/env-$(date +%F).bak      # 0600！里面有库口令与 JWT 密钥
cp -r secrets-admin backup/                    # 管理员口令
bash deploy/up.sh
```

不停机的话 postgres 用 `pg_dump` 更可靠：

```bash
docker exec hca-postgres pg_dump -U hunter hunter | gzip > backup/db-$(date +%F).sql.gz
```

恢复就是反过来：`docker run --rm -v hca_workspace:/dst -v $PWD/backup:/src alpine tar xzf /src/xxx.tgz -C /dst`。

### 4.4 日志与审计

| 文件 | 在哪 | 内容 |
|---|---|---|
| 工具审计 | 卷 `hca_workspace` 的 `.atomcode/audit.jsonl` | 每次工具调用一行：时间、会话、用户、工具名、参数摘要、耗时、结果大小、成功/失败 |
| 权限判定 | 同目录 `guard.jsonl` | 每次 PreToolUse 的判定与理由（哪些被拒、为什么） |
| 预算记账 | 同目录 `budget.jsonl`（**默认不开**） | 每轮的 token 与工具次数 |
| 容器日志 | `docker compose -p hca logs` | 按服务看 |

看审计：

```bash
docker exec hca-daemon sh -c 'tail -5 /workspace/.atomcode/audit.jsonl' | python3 -m json.tool
# 今天各工具被调了多少次
docker exec hca-daemon sh -c 'cat /workspace/.atomcode/audit.jsonl' \
  | python3 -c "
import sys,json,collections
c=collections.Counter(json.loads(l)['tool'] for l in sys.stdin if l.strip())
[print(f'{n:5d}  {t}') for t,n in c.most_common()]"
```

审计文件超过 `HCA_AUDIT_MAX_MB`（默认 64）会轮转成 `.1`，只留一代 —— 要长期留存请
配 `HCA_AUDIT_WEBHOOK` 往你自己的日志系统送（异步、失败不影响对话）。

### 4.5 会话文件与长期增长（M5 实测）

会话落在 daemon 容器的 `/data/atomcode/sessions`（卷 `hca_atomcode-home`），
**每个会话 5–6 个文件**（`.jsonl` 正文 + `.meta` + `.ui.json` + `.rewind.json` + 锁）。
**上游没有自动清理**，长期跑会一直涨。

```bash
docker exec hca-daemon sh -c 'du -sh /data/atomcode/sessions; find /data/atomcode/sessions -type f | wc -l'
# 清 90 天前的旧会话（**先确认没有活跃回合**）
docker exec hca-daemon sh -c 'find /data/atomcode/sessions -type f -mtime +90 -delete'
```

每轮实测增量与内存趋势见 [`docs/stability-report.md`](./stability-report.md)
（4 小时浸泡、48 轮真实对话的逐轮采样）。那份报告的第 8 节是完整的运维建议。

一条最要紧的：**`/health` 与 `/mcp/status` 全绿不代表能用**
（待办池 P0-10 / P0-12 / P0-13 三条都是"面板全绿但模型其实废了"）。
可靠的探活是**真发一条消息**，判据是「调到了 `mcp__*` 工具」而不是「HTTP 200」：

```bash
python3 tools/e2e/web_turn.py --ask "600519 现在什么价？" --name daily-probe
```

### 4.6 MCP 返回的大小闸（v0.1.1 加）

AtomCode 内核对超过 16 KB 的工具返回会砍成头尾各 4 KB 且 JSON 断裂（待办池 P0-11）。
我们在 MCP 侧先裁，两个环境变量控制预算（都要**低于 16384**）：

```ini
HCA_MCP_MAX_BYTES=15000      # 6 个 hunter 系 MCP
AKSHARE_MAX_BYTES=15000      # akshare（与 AKSHARE_MAX_ROWS=50 是两道闸，先限行再压字节）
```

调大它们**不会**让模型看到更多 —— 超过 16384 那一刻内核就会接手去砍。
真要更多数据，让模型缩小查询范围，或给 `akshare_call` 传 `columns` 只取需要的列。

### 4.7 预算闸（默认关）

想给一台共享的机器设上限，在 `deploy/.env` 里：

```ini
HCA_BUDGET_ENABLED=1
HCA_BUDGET_DAILY_TOOL_CALLS=500     # 当天工具调用上限（这个计数最可靠）
HCA_BUDGET_DAILY_TOKENS=5000000     # 当天 token 上限
HCA_BUDGET_SESSION_TOOL_CALLS=80    # 单个会话上限
```

然后 `docker compose -p hca up -d daemon`。超限时用户在**发问的那一刻**就被挡住，
并看到"今日已用 x / y，上海时间 xx 重置"的原话。

⚠️ token 计量有前提，务必读一下 `docs/hooks-design.md` §4.3：AtomCode 的会话统计里
`total_tokens` 恒 0，`model_usage` 只有部分轮次有；覆盖不全时会退回用**网关配额差值**，
而那是**按 key 全局**的。工具调用次数一路可靠，所以要硬限额优先用它。

## 5. 安全

装完的默认状态（install.sh 会强制，不满足直接拒绝启动）：

* **只有 web 的 3200 对外**；api / daemon / postgres / redis 都不发布到宿主端口；
* **单用户免登录关闭**（`HUNTER_SINGLE_USER=0`）—— 开着等于谁打开页面谁就是管理员；
* 注册按**邀请码**（`REGISTRATION_MODE=invite`），第一个账号由安装脚本创建，
  口令写在 `<安装目录>/secrets-admin/admin.txt`（0600）；
* 模型 key 只落 `deploy/secrets/llm-key`（0600），**只读**挂进容器，不进环境变量、
  `docker inspect` 看不到；
* `deploy/.env` 0600（里面有库口令与 JWT 密钥）；
* 容器 `no-new-privileges`，daemon 里跑模型的 bash 工具，但被 hook 限制在工作区内，
  而且 **v0.1.1 起 bash 的首词是白名单**（见 §5.1）。

### 5.1 模型的 bash 能跑什么（v0.1.1 改成白名单）

工作区里的 `.hooks/guard.py` 在 `PreToolUse` 上判每一次 `bash` / `bash_start`。
**v0.1.1 之前是黑名单**（列出不许的），M5 复核时一轮就找出 12 条绕过 ——
`python3 x.py`、`cat x.py | python3`、`base64 -d | sh`、`find -exec`、
`awk 'BEGIN{system()}'`、`source`、`eval`、`perl -e`、`node`、`./x.py` …
形态彼此毫无关系。而 `write_file` 本来就允许往 `reports/` 与 `theses/` 写，
**漏网一条就能接成「先写脚本再执行」的完整绕过**（取到的数不进 MCP 层，
拿不到用户身份、不进审计、界面上也认不出来源）。

所以现在是白名单 `BASH_ALLOW`：只收不会写文件、不会联网、不会执行外部代码的
只读工具（`ls` / `cat` / `head` / `grep` / `find` / `wc` / `sort` / `jq` / `echo` …），
解释器（`sh` 族、`python` 族）**只许 `-c` 内联 / `-m` 模块 / 问版本**。

**要放开某个命令**（比如你的工作流真的需要 `awk`）：

```bash
# 工作区在 daemon 容器的 /workspace，落在 compose 卷 hca_workspace
docker exec -it hca-daemon sh -c "vi /workspace/.hooks/guard.py"   # 改 BASH_ALLOW
docker compose -p hca restart daemon
```

⚠️ 两点提醒：

* `.hooks/` 在 `HCA_WORKSPACE_REFRESH=1`（默认）下**每次启动都会用镜像里的模板重铺**
  —— 直接改容器里那份，下次 `up.sh` 就没了。要持久化就改仓库里的
  `distro/workspace-template/.hooks/guard.py` 再重建镜像，或者设
  `HCA_WORKSPACE_REFRESH=0`（那样其他托管文件也不再更新，升级时要自己对齐）。
* 放开 `awk` / `perl` / `node` / `sed` 这一类等于把上面那条绕过路重新打开 ——
  它们都能执行命令或写文件。真需要的话，想清楚你接受的是什么。

**还要你自己做的**：

1. **上反向代理 + HTTPS**。默认是明文 HTTP，登录口令会裸奔在内网。
   `deploy/nginx/` 下有现成的 nginx 片段。
2. **防火墙**只放 3200（或只放反代的 443）。
3 .**别把 3200 直接怼到公网**，除非你已经做了 1 和 2。
4. 定期轮换管理员口令与模型 key（换 key：覆盖 `deploy/secrets/llm-key` 后
   `docker compose -p hca up -d daemon`，不用重建镜像）。

模型这条路会把什么送出去：**你在对话里说的话、模型决定调用的工具的参数与返回**。
持仓文件本身不会被整份上传（模型只能通过 MCP 按需查询），但它查到的内容会进 prompt。
要彻底不出网就换 Ollama 通道（§8）。

## 6. 模型通道

安装时三选一，装完想换就改 `deploy/.env` 再 `docker compose -p hca up -d daemon`：

| 通道 | `.env` 关键项 | 说明 |
|---|---|---|
| **OneAPI（默认）** | `HCA_LLM_UPSTREAM_URL=https://hunter.agentpit.io/api/saas/llm/v1`<br>`HCA_LLM_BASE_URL=http://llm-shim:3999/v1`<br>`HCA_LLM_MODEL=hunter-chat` | HunterCode 的 OpenAI 兼容网关（Gemini 3.8）。也可填自建 OneAPI。经 llm-shim 兜底修协议 |
| **自带官方 Key** | `HCA_LLM_BASE_URL=<你的 /v1>`<br>`HCA_LLM_MODEL=<模型名>` | 任何 OpenAI 兼容端点。直连，不经 shim |
| **本地 Ollama** | `HCA_LLM_BASE_URL=http://host.docker.internal:11434/v1`<br>`HCA_LLM_MODEL=<你 pull 的模型>` | 完全离网。**必须选支持工具调用的模型**，否则 MCP 一个都用不上 |

### 6.1 网页上显示的模型名

输入框右下角那个模型选择器，显示的**不是**请求用的模型 ID，而是两个显示名变量：

| 变量 | 管什么 | 装完之后长什么样 |
|---|---|---|
| `HCA_LLM_MODEL_LABEL` | 模型名（下拉项与按钮上那一行） | `Gemini 3.8 Flash（全局生效）` |
| `HCA_LLM_PROVIDER_LABEL` | 下拉里的分组标题 | `Google Gemini` |

规则：

- **请求用的模型 ID 一个字都不改**。OneAPI 通道发出去的仍然是 `hunter-chat`，
  换显示名不影响任何调用、也不影响会话里已经存下的 `provider/model` 键。
- 两种写法：整串当一个名字（`Gemini 3.8 Flash`，只在**该通道只有一个模型**时生效），
  或按 ID 逐个指定 `hunter-chat=Gemini 3.8 Flash,hunter-deep=Gemini 3.1 Pro`。
- **不填就显示原始 ID**（`hunter-chat` / `oneapi`）。代码里没有任何内置猜测 ——
  自建 OneAPI 的 `hunter-chat` 背后可能是别的模型，写死一个名字就是骗人。
- `install.sh` 按通道给默认值：OneAPI **且网关地址就是官方那个**时填实测出来的
  Gemini 名字；自建 OneAPI 留空；official / ollama 直接用你填的模型名当显示名，
  分组标题分别是「自带官方 Key」「本地 Ollama」。也可以 `--model-label` /
  `--provider-label` 显式指定。

OneAPI 通道那两个名字是**实测**来的，不是照抄文档（2026-09-22 19:51 香港环境）：

```bash
curl -s -H "Authorization: Bearer $KEY" \
  https://hunter.agentpit.io/api/saas/llm/v1/models
# {"data":[{"id":"hunter-chat",...,"display_name":"Gemini 3.8 Flash"},
#          {"id":"hunter-deep",...,"display_name":"Gemini 3.1 Pro"}]}
```

同一时刻让 `hunter-chat` 自报身份，回的是 `gemini-3.8-flash`，两边对得上。
注意 `POST /chat/completions` 的响应里 `model` 字段回显的是别名 `hunter-chat`，
**从那里看不出真实模型**，要看 `/models`。

改完显示名要重建 web 容器才生效（它是 BFF 在运行时读的环境变量）：

```bash
docker compose -p hca --env-file deploy/.env -f deploy/docker-compose.yml up -d --no-deps web
```

### 6.2 Ollama 通道（Linux）

**Linux 上跑 Ollama 要多做一步**（M5 在真机上跑通之后才写准的，之前这一段是错的）：

1. `extra_hosts: host.docker.internal:host-gateway` —— **v0.1.1 才补进 compose**。
   v0.1.0 及更早版本里没有这一行（文档却写着"已配"），容器根本解析不出这个名字，
   表现是「网页能开、发消息没回答」。
2. **Ollama 必须监听在容器够得着的地址上**。`ollama serve` 默认只听 `127.0.0.1`，
   而容器走的是 docker 网桥（`host.docker.internal` → 172.17.0.1），**连不上**。
   要么 `OLLAMA_HOST=172.17.0.1 ollama serve`（只在宿主与容器间可见，**不对公网**），
   要么 `OLLAMA_HOST=0.0.0.0`（**这会对外暴露 11434，务必配好防火墙**），
   要么在 `.env` 里直接把 `HCA_LLM_BASE_URL` 填成宿主的内网 IP。
3. **不需要 API key** —— `install.sh` 对 ollama 通道不再要求 key（v0.1.1 修，之前
   非交互安装必须编一个假 key 才能过）。

实测（测试机 2 核 8G，模型 `qwen2.5:1.5b`）：装完走网页真发一条消息，
**203.9 秒、172 字、`stop_reason=stopped`**。能用，但 2 核 CPU 上慢到只适合试跑；
而且小模型基本不理会"用中文回答"这类约束，投研场景建议用带工具调用能力的更大模型。

换通道后 key 校验可以手动重跑：

```bash
bash deploy/install.sh --status      # 里面有通道信息
curl -fsS -H "Authorization: Bearer $(cat deploy/secrets/llm-key)" <base_url>/models | head -c 300
```

## 6.3 性能开关（I2）

四个都在 `deploy/.env` 里，改完 `docker compose -p hca up -d daemon llm-shim` 生效。
**默认值就是我们实测下来最快的那一组**；下面写的是「想恢复上游行为时改成什么」。

| 变量 | 默认 | 管什么 | 恢复上游行为 |
|---|---|---|---|
| `HCA_LLM_TOOL_DENY` | 17 个工具名（见 compose 注释） | 在 llm-shim 这一跳把用不上的工具从请求里摘掉。AtomCode 把 atomgit_* 与代码智能工具族**无条件** mount 给模型（`assemble.rs:225`，没有任何 config 或环境变量能关），投研场景一次都用不上却每轮重发一遍 schema | 设成空串 |
| `ATOMCODE_AI_SESSION_NAMING` | `0` | 上游每轮对话结束后会**再发一次模型请求**给会话起标题。本发行版的会话标题由 Web 侧自己管 | `1` |
| `HCA_HOOKD` | `1` | hook 常驻服务。上游每触发一次 hook 就 spawn 一个 python，而 guard + audit 是**每次工具调用都要跑**的两个 | `0`（退回每次起 python，判定完全一致） |
| `HCA_MCP_DISABLE` | 空 | 逗号分隔的 MCP server 名，铺 `.mcp.json` 时去掉。**用不上的数据源关掉能省下一整块工具 schema** | 保持空 |

关于 `HCA_LLM_TOOL_DENY` 的一句话：工具是在 **llm-shim** 这一跳摘的，
**内核那边仍然注册着**。万一模型凭记忆硬凑一个调用，照样能执行 ——
不会出现「说有却调不动」的死角。

实测数字（每一项的收益、以及合起来的前后对比）在
`docs/开发文档/I2-性能优化报告.md`。

## 7. 国内网络

三样东西可能慢或拉不动：Docker Hub 基础镜像、npm 包、PyPI 包。都可以换源：

```bash
bash install.sh \
  --image-prefix docker.m.daocloud.io/ \
  --npm-registry https://registry.npmmirror.com \
  --pip-index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

对应 `deploy/.env` 的 `HCA_BASE_IMAGE_PREFIX` / `HCA_NPM_REGISTRY` / `HCA_PIP_INDEX_URL`
（前缀**要带结尾的斜杠**）。

两点注意：

1. `api` 镜像在 GHCR（`ghcr.io/agentpit-io/hunter-community-api:1.2.0`）。GHCR 拉不动就
   自己转存到内网仓库，再 `--hunter-registry <你的仓库>`。
2. AtomCode 官方二进制是从 npm 取的，**换源之后 sha256 校验照旧** ——
   镜像源上的包和 `pins.lock` 对不上会**直接构建失败**。这是有意的：宁可装不上，
   也不要装上一个来路不明的二进制。

## 8. 完全离网部署

1. 在一台能出网的同架构机器上构建并导出镜像：

   ```bash
   bash deploy/up.sh            # 先在联网机上构建出 hca-daemon / hca-web / hca-llm-shim
   docker pull ghcr.io/agentpit-io/hunter-community-api:1.2.0
   docker pull postgres:16-alpine && docker pull redis:7-alpine
   docker save hca-daemon:dev hca-web:dev hca-llm-shim:dev \
     ghcr.io/agentpit-io/hunter-community-api:1.2.0 postgres:16-alpine redis:7-alpine \
     | gzip > hca-images.tgz
   ```
2. 拷到离网机：`gunzip -c hca-images.tgz | docker load`
3. 拷一份代码目录过去，然后：

   ```bash
   bash deploy/install.sh --non-interactive --yes --no-build \
     --dir /opt/hca --channel ollama \
     --base-url http://<宿主IP>:11434/v1 --model <你的模型> \
     --allow-unverified-key
   ```
4. 离网时 AKShare 那类公网数据源当然也取不到 —— 那 3 个 MCP 会**明确报错**而不是
   假装有数据。自选 / 持仓 / 组合这些走本机 api 的功能照常。

## 9. 排障速查

| 现象 | 查什么 |
|---|---|
| `install.sh` 说 key 校验没过 | 它会把接口的**原始返回**打出来。401/403 = key 不对；超时 = 地址不对或出不了网 |
| 构建卡在 `npm run build` 后 OOM | 内存不够。`HCA_WEB_BUILD_NODE_OPTIONS=--max-old-space-size=2048` 再试，或换机器构建 |
| `daemon` 起来但 `/mcp/status` 有 `connecting` | 2 核机器上 9 个 MCP 同时 initialize 会超时。`.mcp.json` 里 `timeout_ms` 已调到 120000；机器忙时重启一次 daemon |
| 点"历史对话"之后模型说自己没有工具 | 已知缺陷 P0-10（切会话后 MCP 掉线），BFF 已自动补 `mcp/reload` + 等就绪。还出现就 `docker compose -p hca restart daemon` |
| 模型自己写 python 抓数据 | 应该被 guard 拦住。`tail guard.jsonl` 看有没有 deny 记录；没有就说明命中了新的绕法，请报 issue |
| 一轮跑很久没结束 | `HCA_TURN_TIMEOUT_MS`（默认 570000 = 9.5 分钟）。工具链长的问题确实会跑几分钟 |
| 策略中心 / 模型回测页打不开、接口 403 | api 的判据是「JWT role == `ADMIN`（**大写**）或 email 在 `HUNTER_ADMIN_EMAILS` 白名单」，而库里 role 存的是小写 —— 白名单是唯一进得去的路。`up.sh` 会按 `HCA_ADMIN_EMAIL` 自动补；手工加人就在 `.env` 里追加（逗号分隔）后 `docker compose -p hca up -d api` |
| 回测看板一直是 `--%` | **不是故障**。它统计 Kronos 预测的准确性，要出数得同时满足：自选股非空、配了 `KRONOS_API_KEY`、**至少两天**的预测重叠（每交易日 16:30 自动跑）。没满足时它如实显示 `--%`，不编数字 |
| 网页所有消息都报 `upstream_unreachable` | 多半是 daemon 的 `/live` 被一个"孤儿 runtime"占住了（待办池 P0-12）。转发层会自动尝试收回；还不行就 `docker compose -p hca restart daemon`。**根治办法是别在网页之外再开 `/live` 消费者** |
| 磁盘满 | `docker system df`；审计日志轮转看 `HCA_AUDIT_MAX_MB`；会话记录在 `hca_atomcode-home` |

出问题要提 issue 的话，带上这三样（都不含密钥）：
`bash deploy/up.sh --status` 的输出、`docker compose -p hca logs --tail 200 daemon`、
`docker exec hca-daemon sh -c 'tail -20 /workspace/.atomcode/guard.jsonl'`。
