## 0. 一页结论

- **总工作量**：约 25–35 个 AI 辅助开发人日；第 1 周验证、第 2 周迁移、第 3 周发布、第 4 周缓冲。
- **核心策略**：单源多发行版。SKILL、MCP、Web 前端与量化后端保持唯一源；opencode 与 AtomCode 作为两个 `distros/` 目录并行维护。
- **最大风险**：AtomCode 是编码 Agent，系统提示、意图分类、编译校验都面向写代码。把它改造成投研 Agent 的"领域改造"是唯一的不确定项，第 1 周必须给出量化结论。
- **纪律**：不改内核。只依赖四个外部接口——daemon HTTP/SSE API、MCP、hook、skill。锁定 tag，每月评估一次升级。
- **不做的事**：P0 不做多租户 Demo 站（Demo 站继续跑 opencode 版）；不迁移 opencode 的多端客户端。

## 1. AtomCode 结构速览

### 1.1 四个 crate

| crate | 职责 | 与我们的关系 |
|---|---|---|
| atomcode-core | Agent 引擎：工具、上下文、语义分析、LLM 通信；无 TUI 依赖 | 不碰内核，只用它暴露的 skill / hook / MCP / provider 机制 |
| atomcode-tuix | 终端 UI | 不用 |
| atomcode-cli | CLI 入口、OAuth 登录、无头模式 `-p` | 可选（桌面/脚本场景） |
| atomcode-daemon | HTTP/SSE API 服务，可独立部署 | **主要接入点**，Web 后端对接它 |

### 1.2 我们要用的外部接口

| 接口 | 机制 | 备注 |
|---|---|---|
| daemon API | `/chat`（SSE 流式）、`/sessions`、`/config`、`/auth`、`/models`、`/mcp`、`GET /skills`；WebUI token 鉴权 | 默认绑 127.0.0.1:13456；权限模式 BypassAll（服务端场景可接受） |
| MCP | 项目目录下 `.mcp.json`；HTTP 与 stdio 传输；`/cd` 切目录时自动重载 | 我们 3 个 MCP server 直接可挂 |
| Skill | `.atomcode/skills/*.md` Markdown 技能，支持参数展开；可作斜杠命令 | 我们 29 个 SKILL 需格式转换 |
| Hook | 13 个扩展点（Message / Turn / Tool / Session / System 级），pre/post 可 modify / deny；shell 脚本或 webhook（同步 / 异步批量） | 替代 opencode plugin |
| Provider | `config.toml` 中 type=openai 的任意 OpenAI 兼容 base_url；Claude / Ollama 原生 | 我们的大模型路由器可作为一个 provider |
| 项目指令 | 根目录 `.atomcode.md`（优先）或 `AGENTS.md` 注入系统提示 | 领域改造第一层 |

### 1.3 需要警惕的编码倾向

| 模块 | 行为 | 对投研场景的影响 |
|---|---|---|
| `agent/task_classifier.rs` | 把用户消息分为 BugFix / FollowUp / FeatureDev / Question / Command / SingleFileEdit | 投研问题多数落到 Question，但可能触发只读限制与 "Analyze first" 前缀 |
| `agent/mod.rs` auto_compile / auto_diagnose | 编辑后自动编译、扫日志找异常 | 研究工作区没有编译对象时行为不确定 |
| `project_context.rs` | 扫描 3 层目录树 + tree-sitter 符号 + tech stack 探测 | 可以反向利用：让它扫到的是研究资产 |
| `config/mod.rs` DEFAULT_SYSTEM_PROMPT | 124 行编码规则 | 需确认能否完整替换而非仅追加 |
| 内置工具集 | edit_file / write_file / search_replace / bash 等 | 需用 hook 白名单收窄 |

## 3. 领域改造方案（重点）

目标：不改内核，用 AtomCode 暴露的机制把编码 Agent"驯成"投研 Agent。分三层，由轻到重，逐层验证。

### 第一层 · 纯配置

1. `.atomcode.md` 写完整投研角色、研究流程、输出规范、风险提示叠加层规则，覆盖默认提示的编码倾向。
2. hook 的 pre-message 扩展点补充或改写系统上下文（如注入当日行情摘要、用户持仓约束）。
3. hook 的 pre-tool deny 关闭代码编辑类工具：`edit_file`、`write_file`、`search_replace`、`auto_fix`；**保留** `bash`（跑 Python 量化脚本）、`read_file`、`grep`、`glob`、`web_search`、`web_fetch`、`use_skill` 与全部 MCP 工具。
4. `config.toml` 配置 provider：自有路由器 + 用户自选官方 Key。

### 第二层 · 工作目录设计

把 AtomCode 的"项目"重定义为"研究工作区"：

```
workspace/
  README.md              # 工作区说明，被 project_context 扫到
  requirements.txt       # 让 tech stack 识别为 Python 环境，auto_compile 有明确对象
  .atomcode.md           # 领域提示
  .mcp.json
  .atomcode/skills/      # 由 skills-src 构建生成
  holdings/              # 持仓文件（本地，不出硬盘）
  theses/                # 投资记忆体：买入论点、关键假设、验证记录
  factors/               # 因子定义与回测配置
  reports/               # 生成的研报与图表
  scripts/               # 用户自定义 Python 脚本
```

project_context 扫描到的是研究资产而非代码，反而成为优势。

### 第三层 · 最小 fork 补丁（仅在前两层不够时）

- `task_classifier` 与 `auto_diagnose` 增加 config 开关（默认开，垂直发行版关）。
- `DEFAULT_SYSTEM_PROMPT` 支持被 config 完整替换，而非仅追加。

两个补丁都很小，**作为 PR 提回上游**——这是给 AtomGit 团队看得见的生态贡献，也让"定制我的领域"对所有垂直用户成立。

### 决策点（第 1 周末）

用 5 个典型投研问题做 A/B 对比（AtomCode 第一+二层 vs opencode 版），按准确性 / 工具调用正确率 / 输出规范 / 步数与耗时四项打分。**达到 opencode 版 80% 以上不做 fork；否则做第三层并同步提 PR。**

## 4. 架构：单源多发行版

```
hunter-community/
  skills-src/            # SKILL 唯一源（现有 Markdown），两个发行版从这里构建
  mcp/                   # truesource / kronos / akshare，两边共用
  distros/
    opencode/            # 现有 plugin、配置、compose（不动）
    atomcode/
      .atomcode.md
      config.toml.example
      .mcp.json
      hooks/             # 4 个 hook 脚本 + hooks.toml + webhook 配置
      skills/            # 构建产物，不手改，.gitignore 或 CI 生成
      docker-compose.yml
      install.sh
      pins.lock          # 锁定的 AtomCode tag 与二进制校验和
  web/
    backend/
      agent_adapters/
        base.py          # AgentAdapter 抽象：create_session / chat_stream / list_tools / cancel
        opencode.py      # 现有实现
        atomcode.py      # 新增：对接 daemon SSE
    frontend/
  tools/
    build_skills.py      # skills-src → 两种目标格式
    sync_upstream.sh     # 上游 tag 变更时的差异报告
```

Web 后端通过环境变量 `AGENT_BACKEND=opencode|atomcode` 切换适配器。国内版与国际版长期并行的维护成本由此可控。

## 5. 多租户与 Demo 站

AtomCode daemon 是本地优先、单用户设计（绑 loopback、BypassAll 权限、单工作目录）。

| 场景 | 方案 |
|---|---|
| 私募私有化部署 | 一家一套，daemon + web + MCP 同机，无需改动 |
| 个人桌面版 | 同上，本机运行 |
| hunter-community.agentpit.io 多用户 Demo 站 | **P0 不做**。继续跑 opencode 版。若未来需要：每用户一个 daemon 容器 + 工作目录隔离 + Web 层按用户路由到实例 |

AtomCode 版以"私募单机部署 + 本地桌面"形态演示，与"推理在你机器上跑，仓位不出你硬盘"叙事一致。

## 7. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 编码倾向压不住，投研效果明显差于 opencode 版 | 中 | 第 1 周量化对比，尽早决定 fork 补丁并提 PR |
| AtomCode 一天多次发版，接口漂移 | 高 | 锁定 tag（pins.lock），只依赖四个外部接口，每月评估一次升级 |
| daemon 单用户设计 | 确定 | P0 不做多租户，Demo 站保留 opencode 版 |
| 默认工具集面向代码，误操作风险 | 中 | hook 层白名单，只放行研究所需工具；bash 命令加二次拦截 |
| 上游 MIT、我们 Apache-2.0 分发 | 低 | 兼容；保留上游 LICENSE 与版权声明 |
| daemon SSE 事件格式与 opencode 不同，前端 Artifact（Kronos 图表）渲染断裂 | 中 | 适配层统一为内部事件模型，前端不感知后端差异 |

### TP-04 · 4 个 hook 完整实现

```
任务：把 opencode 版的 auth / audit / guard / budget 四个 plugin 迁移为 AtomCode hook。

前置：先读 distros/opencode 中四个 plugin 的源码，逐个写出它们的职责、触发点、依赖的后端接口。

映射与实现：
1. audit → 使用 AtomCode 内置的工具审计 hook 为基础，扩展为把每次工具调用（名称、参数摘要、耗时、结果大小、会话 ID）以异步批量 webhook 发到 HunterCode 后端 /api/audit。确认现有后端接口格式，不一致则写适配。
2. guard → 在 TP-03 的 tool-guard.sh 基础上补齐：白名单外工具 deny；bash 危险模式拦截；读取工作区外路径 deny；对 MCP 工具按会话级配置放行。
3. budget → 用 Turn 级 hook 统计每轮 token 与工具调用次数，累计到会话；超过 config 中阈值时通过 pre-message hook deny 并返回提示。阈值与计费口径从后端 /api/budget 拉取（同步 webhook）。
4. auth → 不在 hook 层实现。改为：daemon 由 Web 后端反向代理，用户身份在 Web 层校验后以 header 传入；hook 只负责把 Web 层传入的用户标识写进审计事件。写清楚这一设计决策与原因。

工程要求：
- 每个 hook 独立文件，放 distros/atomcode/hooks/，统一由 hooks.toml 注册，注明扩展点、优先级、同步/异步。
- 提供 atomcode hooks test 可运行的测试用例。
- webhook 失败不能阻塞对话（异步批量），budget 的同步 webhook 要有超时与降级策略。

输出物：
- distros/atomcode/hooks/{audit.sh, guard.sh, budget.sh} 与 hooks.toml
- distros/atomcode/docs/hooks-design.md（含 plugin → hook 映射表与 auth 上移说明）
- 测试记录

验收：四项行为各有一个可复现的测试场景通过；对话主流程在 webhook 后端不可达时仍可用。
```
