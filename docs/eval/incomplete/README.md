## 这次暴露的两件事

### 1. `--min-quota` 这道闸的阈值定得不对

`run_ab.py` 每次开跑前查配额，低于 `--min-quota` 就停批。本轮为了把剩余额度
用满，把它从默认 30 万降到了 **12 万**。开跑前剩 259 634，过了闸；
而这一次运行**自己就要 264 086** —— 闸放行了一个它拦不住的运行。

闸的阈值应该按**观测到的单次最大开销**来定，不是拍一个整数。本批 HCA 侧
单次开销实测跨度极大：52 030（q4）～ 669 925（q2 r2），中位数约 8 万。
30 万的默认值能拦住大多数，但拦不住 q2 那一档。M3 若还要跑评测，
闸应改成「剩余 < 本题历史最大开销 × 1.2 就不开跑」。

### 2. 这一次里模型**真的调了 `fetch_output`**

第 14 次调用是 `fetch_output(artifact_id="e6aef62ac7a789c2", limit=4000, offset=0)`
—— 这是整批 25 次运行里**唯一一次**主动去取被截断的完整返回。
对 P0-11 是个正面信号：能力在，只是不稳定。两次被截断的返回全长
121 KB / 186 KB，远超 16 KB 阈值，模型这次意识到了缺数据。

**但它也正是这次烧掉 26 万 token 的原因之一**：`fetch_output` 取回的内容
同样进上下文，而 9 轮里上下文一直在涨。P0-11 的绕法因此不能只靠「叫模型去
fetch」，还得把 MCP 侧的返回本身压小。
