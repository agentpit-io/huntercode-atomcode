# I4 · 响应时间专项评测 —— 这一批数据是怎么来的

> 任务书（用户 2026-09-23 11:25）：「需要相同数据库和服务器，评估响应时间，
> 对比 opencode，重点看响应时间」。

## 1. 把变量压到只剩引擎

| 变量 | 做法 | 证据 |
|---|---|---|
| 机器 | 专用评测机 `hca-bench-01`（8 核 31G，只跑评测，不与任何项目共用）；两侧栈同时在机器上，**交错执行、每轮换先手** | 每批的 `same-db-proof.txt` 头两行记了 `hostname` 与 `uptime`；每一次运行的 `loadavg_before/after` 在 `index.json` 里 |
| 数据库 | **两边共用同一个 api 进程、同一个 postgres 实例、同一个库、同一行用户** | 每批开跑前跑一次 `deploy/eval/i4-same-db-proof.sh`，输出存 `<批次>/same-db-proof.txt`，六条判据全绿才开跑 |
| 数据 | 每一次运行前把两侧工作区账本恢复成同一份种子（`run_ab.py` 的 `reseed`）；用户域数据在同一个库里，本来就是同一份 | `index.json` 每行的 `reseed_rc` |
| 缓存 | 两边共用同一套 api + redis + postgres，缓存状态天然一致；每批**先预热一次、数据丢弃** | 预热跑进 `<批次>/warmup/`，汇总脚本不读它 |
| 模型通道 | 同一个网关、同一把 key、同一个模型名 `hunter-chat` | 每一次运行记 `quota_used_before/after` 与差值 `quota_delta` |

### 1.1 为什么没按任务书那条「基线栈改指到 HCA 那套 postgres」去改

因为**不需要改，现状已经比那条更强**。评测拓扑里本来就只有一套后端：

* HCA 侧只起 `daemon` + `llm-shim`（`deploy/eval/docker-compose.i2.yml`），
  它的 hunter 系 MCP 通过 `HERMES_API_URL` 打**基线那套 api**
  （`deploy/eval/docker-compose.hca-api.yml`，网络别名 `hunter-api`）；
* 社区版 `opencode` 打的是**同一个容器**（服务名 `api`）；
* 那个 api 只连一个 postgres，而整台机器上**只有这一个 postgres 容器**。

所以两边共用的不是「两个同构的库」，是**同一个 api 进程 + 同一个库 + 同一行用户**。
任务书里那条退路（两库同构 + 每次恢复同一份 dump）因此没有被触发，
也就没有「两种口径各一组数」这回事 —— 只有一种口径，而且是更强的那种。

## 2. 六条同库判据（`deploy/eval/i4-same-db-proof.sh`）

1. 整台机器在跑的 postgres 容器只有 1 个；
2. 两个引擎的 `HERMES_API_URL` 在各自容器里解析出来的 IP，**都属于同一个 api 容器**；
3. 那个 api 的 `DATABASE_URL` 解析出来就是那唯一的 postgres，库名与实例
   `system_identifier` 都打出来；
4. `users` 表里那一行的 id == HCA daemon 的 `HUNTER_USER_ID` ==
   社区版会话登记表 `chat_session_owner` 里的 `user_id`；
5. / 6. **真调用**：两个引擎各打一次 `/api/internal/quant/market_screen`，
   每次调用前后各读一次 `pg_stat_database.xact_commit` —— 事务数涨了，
   才算这次调用真的落到了这个实例上（不是看配置，是看行为）。

任何一条不成立，`i4-batch.sh` 直接退出，不开跑。

## 4. 分段计时的口径

见 `tools/eval/i4_summary.py` 的模块注释（那份是权威口径，报告与
`summary.json` 都由它生成，不手抄）。一句话版本：一次运行切成
**模型段 / 工具段 / 出字段 / 收尾段**，HCA 侧四段之和 == 墙钟（实测残差 < 1 ms）；
社区版的收尾段**量不到**（阻塞 POST，没有独立的结束事件），写 `null`，
它的上界就是残差（实测 24～32 ms）。

两个首字延迟都给：

* `ttft_ms` = 第一块正文到达 —— 但本部署的人设要求模型在一批工具调用前
  **先发一行「路标」**，所以这一块正文可能是进度提示而不是答案；
  表里「其中路标」那一列标出了 n 次里有几次是这样。
* `ttft_answer_ms` = **末轮**第一块正文开始 = 真正的答案开始出字。
  两边同一口径，不受路标影响。**跨产品比较以这一个为准。**

## 5. 「原样」与「都真做题」两套数

I1 §3.11 记过：`q2` 上社区版有几次**没做这道题** —— 反过来要用户把论点贴出来
（而 `theses/601088.md` 就在它自己的工作区里）。这种运行又快又短，
混进中位数里会让对照组显得很快。所以每道题给两套数，判据是**事前写死、
与耗时无关**的一条正则（`i4_summary.PUNT_BACK`），只认「向用户索要材料」这一类措辞，
且**不作用于 `q4` / `q10`**（那两道题的正确答案本来就可能是「拿不到」「我不做」）。
在 I1 的 108 次运行上试过：命中 3 次，正好是 I1 §3.11 点名的那 3 次，没有误伤。

## 6. 这批数据不能拿去做什么

* **不能跨天和 I1 / I2 / I3 的绝对值比。** I3 §1 用同一份配置隔一夜重测，
  D 维度差了 1.4 分 —— 漂的是 HCA 这种大请求在不同时段拿到的服务质量
  （待办池 U-19）。能比的只有**同一批次内两边的相对关系**。
* **不能当评分用。** 这一轮不打四维分，只量时间；题目的对错口径仍以 I1 为准。
* HCA 的代码是 **main（v0.2.1）**，不是 I1 当时的 v0.2.0；Kronos key 与 I1 一样是**接上的**，
  所以 `q4` 的 B 线数字与 I2 / I3 不可比（I2/I3 那几轮 key 是空的）。

## 7. 目录里有什么

```
docs/eval/i4/
  README.md              ← 这份
  summary.json           ← 机器可读，给 PPT 取数；每个数字带 source
  tables.md              ← 逐题分段计时表（由 i4_summary.py 生成）
  hook-bench.json        ← HCA 侧 hook 开销直测（社区版没有 hook 机制）
  idle-b/ i4-b/ idle-a/ i4-a/
      <题>-<边>-r<n>.json      结构化记录（含全文、瀑布、配额差值）
      <题>-atomcode-r<n>.sse   HCA 侧原始 SSE（带到达时刻注释行，可完整重放）
      <题>-opencode-r<n>.raw.json  社区版原始消息
      <题>-*-r<n>.shim.jsonl   llm-shim 的请求瀑布追踪（只记尺寸与耗时）
      index.json               每次运行的 rc / 负载 / 剩余配额 / 账本恢复结果
      same-db-proof.txt        本批开跑前的同库取证
      warmup/                  预热，**汇总时不读**
```
