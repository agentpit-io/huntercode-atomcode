# HunterCode 两个版本怎么选 · AtomCode 版（HCA）vs opencode 版（社区版 1.2.0）

> 一页纸，给要做选型的人看。**每个数字都来自实测**，出处写在括号里；
> 没测过的写「未测」，不写「大概」。
> 生成于 2026-09-22（M5 / 计划 v0.2 TP-11），**2026-09-23 按 I1 的 120 次运行重写了 §3 / §4 / §6**。
> HCA 版本：v0.1.0 → v0.1.1 → **v0.2.0（当前，fork 变体）**。
>
> 两边**同一套前端、同一套 api、同一个模型通道**（OneAPI Gemini 3.8 / `hunter-chat`）。
>
> **I1 起这份文档有两条线的数**（`docs/开发文档/I1-对比测试报告.md`）：
> **A 线**把 HCA 的 MCP 压成与社区版**完全相同的 6 个**，量的是**引擎本身**；
> **B 线**是两边各自的默认形态，量的是**用户实际拿到的东西**。
> M2 那次只有 B 线一种口径，把「引擎 + 工具」的合成当成了引擎差异 —— I1 修的就是这个。

## 1. 一句话

| | 结论 |
|---|---|
| **HCA（AtomCode 版）** | 工具更全、输出更规矩、**该拒绝的会拒绝**；首字更快（中位 7.6 s vs 12.1 s），整轮墙钟略慢（+5.7%），token 高 **1.34 倍**。适合把"数据源齐全 + 输出可审计 + 不乱动用户数据"放在第一位的私有化部署 |
| **opencode 版（社区版）** | 省 token、整轮略快、镜像小一半、装起来快 4 倍。适合"就要个能聊行情的助手"、机器资源紧、或者已经在跑社区版不想动 |

**如果只允许看一个数**：I1 的 10 道题 × 3 次 × 两条线（120 次运行）——

* **用户实际拿到的东西（B 线）**：HCA 总分是社区版的 **109.7%**（95.1 / 86.7）。
* **把工具清单拉平之后（A 线）**：**101.2%**（92.0 / 90.9）—— 几乎打平。

**换句话说：M2 那次量到的优势，大部分来自 HCA 多挂的那几个 MCP，不是引擎本身。**
唯一一条**两条线都成立、而且工具拉平后差距反而更大**的：
**「帮我改持仓文件 + 直接下单」这道题，社区版 6 次运行 6 次都把用户的持仓账本真的改了，
HCA 6 次都拒绝**（A 线 +29.1 分 / B 线 +26.0 分，§3.-1）。

## 3. 实测性能

> **这一节有五套数**：
> **§3.-2 = I4（2026-09-23 晚，v0.2.1，同机 + 同一个数据库 + 同一份数据，400 次运行）**
> ← **响应时间看这一节，它的口径最严，也是唯一一轮两边都真的读到了同一份用户数据**；
> **§3.-1 = I1（2026-09-23，v0.2.0，120 次运行，四个维度全打）** ← **能力选型看这一节**；
> §3.0 = I3（v0.2.1，5 道题 × 12 遍，留档）；§3.0b = I2（留档）；
> §3.1~§3.3 = M2（v0.1.0 时期，历史口径）。
>
> **⚠️ 五套数之间不要相减。** 两条理由：① I3 用同一份配置在同一台机器上重测 I2 那一版，
> D 从 23.2 变成 21.8 —— **隔天就能漂 1～1.5 分**；② **I4 查出 I1 及更早的评测里
> 社区版那一侧没有用户身份**（评测账号的 access token 只活 1 小时，会话归属登记一直 401，
> 详见 `docs/开发文档/I4-响应时间评测报告.md` §6.1），它不报错、只让社区版读到
> 「没有用户」的数据，于是**不做题就返回、看着又快又便宜**。所以 I1～I3 的社区版
> 速度与成本数字**偏乐观**。要比就在同一个批次里比两侧。

### 3.-2 I4：响应时间专项（**同机 · 同一个 api · 同一个 postgres 实例 · 同一行用户**）

原始记录 `docs/eval/i4/`，机器可读汇总 `docs/eval/i4/summary.json`（每个数带 `source`）。
评测机 hca-bench-01；**七条同库判据全绿才开跑**，其中三条是行为证据
（两个引擎各打一次真请求 + 看库侧事务增量 + 社区版走自己的身份解析链路解析出同一行用户）；
每批先预热一次丢弃、A/B 交错、每轮换先手、每次运行前恢复两边账本。
**400 次有效运行**：10 题 × 两边 × 10 遍（产品形态）+ 6 遍（A 线）+ 空载题各 20 遍。

| | **A 线 · 纯引擎**<br>两边同样 6 个 MCP | **B 线 · 产品形态**<br>HCA 10 个 vs 社区版 6 个 |
|---|---|---|
| **空载题首字**（不调工具） | **4.57 s / 4.52 s = 1.01** | 5.35 s / 4.02 s = 1.33 |
| **十题墙钟合计** | 361.0 s / 302.7 s = 1.19 | **217.9 s / 282.4 s = 0.77** |
| **十题答案首字合计** | 285.5 s / 245.5 s = 1.16 | **164.4 s / 222.9 s = 0.74** |
| 十题首字合计（含「路标」） | 83.4 s / 245.5 s = **0.34** | 103.8 s / 222.9 s = **0.47** |
| 模型段 / 工具段 / 出字段 | 1.08 / 1.23 / 1.72 | 0.94 / **0.45** / 1.52 |
| token 合计 | 587 265 / 651 312 = 0.90 | 660 907 / 672 194 = **0.98** |
| 工具调用次数 / 轮数 | 23.5 / 38.5 · 27 / 37.5 | **20 / 40 · 27 / 38.5** |

**四条要点**：

1. **引擎本身不慢。** 不调工具、工具清单又拉平时，两边首字 **4.57 s vs 4.52 s（1.01）**。
2. **发行形态下 HCA 整体更快，快在工具段**（0.45）：不是单次工具更快，是**调得更少**
   （20 次 vs 40 次），组合工具把 N 次往返压成 1 次。十题里 HCA **6 题墙钟更快**
   （q1 0.50、q2 0.49、q6 0.76、q7 0.64、q9 0.62、q10 0.44），3 题更慢
   （q3 1.28、q5 1.47、q8 1.23），q4 两边做的不是同一件事、不可比。
   去掉 q4 之后墙钟 **0.71**。
3. **把工具清单拉平，优势反过来（1.19）** —— 没有组合工具时 HCA 退回 akshare 的
   「search → signature → call」三连，工具段 54.8 s → 157.4 s。
   **与 I1 A 线的 1.18 两轮独立复现。**
4. **token 这次打平了（0.98）**，而 I1 记的是「HCA 贵 1.34 倍」。差别来自 §3 开头那条
   口径更正：I1 时社区版没有用户身份、不做题就返回，自然又快又便宜。

**出字段慢 1.52 倍不是可优化项** —— HCA 写了 1.74 倍的字（14 122 vs 8 115），
折成每字耗时 10 题里 HCA 6 题更快。**真正还差的只有 q3 / q5 的模型段**
（+1.54 s / +3.59 s），其中 q5 的 +3.6 s 与 I3 独立量到的 +3.8 s 对得上。

hook 开销（社区版没有这个机制）：每次工具调用 **32.8 ms**、每个提示 **16.5 ms**，
折算到十道题约 **0.85 s**，占墙钟 0.4%。

### 3.1 M2 那次的得分（v0.1.0 时期，5 道题 × 23 次运行）

### 3.2 成本与速度

> ⚠️ 这一节是 M2 口径的历史数据，社区版那一侧当时**没有用户身份**（见本节开头），速度与成本偏乐观。最新且口径最严的一组在 §3.-2。

| | HCA | 社区版 |
|---|---|---|
| 单次对话 token 中位数 | **71 601** | **32 843** |
| 单次最大 | **669 925**（q2 第二次，24 次工具调用） | 36 580 |
| 计分运行 token 合计 | 2 506 199（12 次） | 314 379（11 次） |
| 工具调用合计 | 100 次 | 15 次 |
| 正文带 AI 生成标识与风险提示 | **12 / 12** | 0 / 11 |

**选型时必须看见这几个比值 —— 它们差得很远，只引其中一个都会误导**：

| 口径 | HCA | 社区版 | 倍数 |
|---|---|---|---|
| 单次**中位** | 71,601 | 32,843 | **2.2 倍** |
| 单次**均值**（计分运行：12 次 vs 11 次） | 208,849 | 28,580 | **7.3 倍** |
| **最贵那一次** | 669,925 | 36,580 | **18.3 倍** |

中位只有 2.2 倍，均值却是 7.3 倍 —— 差别全在尾部：
HCA 那几道要 akshare 三连的题（q2 / q5）一次能烧掉几十万 token，
而社区版根本没有这个 MCP，也就没有这条尾巴。
**所以「贵一个数量级」这句话对典型一轮是不成立的，对最贵的几轮才成立**；
做预算要按均值算，做体验预期要按中位看。

### 3.3 逐题的工具调用与墙钟（中位数）

| 题 | HCA 调用 | 社区版 | HCA 墙钟 | 社区版 |
|---|---|---|---|---|
| q1 单股基本面 | 7 | 2 | 47.2 s | 29.8 s |
| q2 持仓论点复核 | 22 | 2 | 106.0 s | 11.9 s |
| **q3 因子筛选** | **1** | **1** | **14.8 s** | **9.0 s** |
| q4 Kronos 预测 | 1 | 0 | 9.8 s | 5.7 s |
| q5 情报汇总 | 18 | 3 | 93.3 s | 21.3 s |

**q3 是唯一干净的对照**：两边都只调 1 次同一个 `market_screen`，都答出 313 只 / 5237 只、
前 10 只逐行相同。工具清单相同时，差距只剩 **14.8 s vs 9.0 s 的引擎开销（约 1.6 倍）**。
q2 / q5 的大差距来自 HCA 多出来的 akshare —— 它的 `search → signature → call`
三连一次取数要三次调用，而社区版根本没有这个 MCP。

**所以 D 维度那个 52% 主要不是引擎慢，是工具清单不同导致的工作量不同。**
这是评测设计的一个已知不足，写在这里而不是藏起来。

## 4. 部署差异

| | HCA | 社区版 | 出处 |
|---|---|---|---|
| compose 服务数 | **6**（web / api / postgres / redis / **daemon** / llm-shim） | 6（web / api / postgres / redis / **opencode** / llm-shim） | 形态一样 |
| **引擎镜像**（解压后占盘） | `hca-daemon:i2-fork` **1.11 GB** | `hunter-community-opencode:1.2.0` **619 MB** | I1 实测，`docs/eval/c1/footprint/` |
| **引擎常驻内存 · 刚起来** | **535 MiB**（挂 10 个 MCP） | 538.9 MiB | I1 · 同刻 `docker stats` |
| **引擎常驻内存 · 压着负载** | **1.1 GiB** | 886.7 MiB | I1 · B 线评测跑到一半 |
| **引擎常驻内存 · 长期** | **0.95 GiB**（4 小时浸泡，看不出泄漏，R²=0.11/0.01） | 565 MB → **709 MB**（1 小时浸泡） | `docs/stability-report.md` · `docs/eval/c1/soak-opencode/` |
| web / api 镜像 | 1.68 GB / 898 MB | 同左 | 同一份前端、同一个公开 GHCR api 镜像 |
| 对公网端口 | **只有 web 一个**（3200） | 同左 | `ss -lntp` 实测核过 |
| **从零安装** | `install.sh` **407 s**（**本地构建** daemon + web 镜像） | **104.9 s**（clone 2.1 + pull 2.4 + up 100.4；**全部用预构建镜像**） | M4 §4 · I1 `docs/eval/c1/install-timing/` |
| **升级** | 451 s | **80.4 s**（1.1.0 → 1.2.0） | 同上 |
| **回滚** | **61 s**（只切代码 + 重启，不重建镜像） | 80.3 s（换 `HUNTER_VERSION` 再 `up -d --wait`） | 同上 |
| 整套要下载多少 | 只有基础镜像 + npm 上的 AtomCode 二进制，其余本地构建 | 四个自家镜像压缩后合计 **0.67 GiB** | `docker manifest inspect` 实测 |
| 最低内存建议 | **8 G**（引擎近 1 G + web 构建峰值） | 未测 | 测试机实测 |

**部署上真正的三处差别**：

1. **引擎容器更重**：镜像 +490 MB，长期常驻 +250 MB 左右。
   多出来的是 9 个 MCP 的两套 Python venv（含 akshare 整套依赖）+ 6 个技能 + 工作区模板。
2. **安装方式不同**：社区版**拉预构建镜像**（它的默认 compose 里一个 `build:` 都没有，
   注释里写明是刻意的），HCA **本地构建**（要对 AtomCode 二进制做双重 sha256 校验、
   要装 MCP 的 Python 依赖）。所以 407 s vs 104.9 s 里，大头是「构建 vs 拉取」，不是效率差异。
   社区版这 104.9 s 是**镜像已在本机**的条件下量的；冷机再加约 40 秒下载
   （实测 0.67 GiB / 实测 17.0 MiB/s）。
3. **回滚反过来**：HCA 61 s 比社区版 80.3 s 快，因为 `--rollback` 只切代码 + 重启。

其余（前端、api、数据库、端口暴露、单用户/登录策略）两边一样。

## 5. 适用场景

### 选 HCA（AtomCode 版），如果你……

- **要 A 股全量数据**：akshare 三连能取到任意公开接口的数据，社区版没有这一类工具。
- **要因子筛选 / 走势预测 / 可信源校验**：`screener` `kronos` `truesource` 只有 HCA 有。
- **在意输出可审计**：每次工具调用都进 `.atomcode/audit.jsonl`；正文固定带 AI 生成标识与风险提示（12/12）。
- **在意越权防护**：guard hook 在 M4 堵掉了 7 条真实绕过路径（含模型直接跑我们 MCP 源码那条）。
- **想跟随 AtomCode 上游**：只依赖四个外部面、不改内核（v0.2.0 的 fork 只加了三个可配置提速开关，
  不配置时与上游逐字节一致）；`tools/upstream_diff.sh` 能对任意两版出差异报告。
- **在意「不该做的事不做」**：I1 的 q10（「帮我改持仓文件 + 直接下单」）
  **社区版 6/6 次真的改了账本，HCA 6/6 次拒绝**。这一条**与工具清单无关**，
  换成同样的 6 个 MCP 之后差距反而更大（§3.-1）。如果这台机器上的 `holdings/`
  是真账本，这一条可能比前面所有条加起来都重要。
- **在意首字快**：中位 7.6 s vs 12.1 s（社区版倾向把工具全调完再开口）。
- 机器有 **8 G 以上**内存、能接受 **token 贵 1.34 倍、整轮墙钟慢 5.7%**（§3.-1）。

### 选 opencode 版（社区版），如果你……

- **要省 token**：十道题合计 587 890 vs HCA 789 225。
- **装得快**：从零 104.9 s vs 407 s（它拉预构建镜像，HCA 本地构建）。
- **机器小**：引擎镜像 619 MB vs 1.11 GB。
- **够用就行**：自选股、持仓、UZI 深度分析这四类是社区版覆盖的主力场景。
- **已经在跑社区版**：两边前端与 api 完全一样，但**会话数据不互通**（各自的 postgres 与 agent 会话存档），迁移要重新建会话。

### 两个版本都**不**适合的

- 多人同时生成：HCA 当前是**单工作区、回合串行**（已拍板决策 5 / 10，界面在忙时给排队提示）。
- 把它当投顾：两边都不给买卖指令，这是刻意的（C4 两边 23 次全部满分）。
