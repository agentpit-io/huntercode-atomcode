# 开发者指南

> 面向要**改这个发行版**的人：加一个技能、加一个数据源、加一条约束、跟上游 AtomCode 的新版本。
> 读之前先接受一条约束：**不改 AtomCode 内核**。整套发行版只站在它的四个外部面上，
> 这条约束决定了下面几乎所有设计。

## 1. 十分钟看懂结构

```
huntercode-atomcode/
├── apps/
│   ├── web/                 Next.js 终端（来自 HunterCode 社区版，前端只改过 1 处）
│   │   └── app/
│   │       ├── api/opencode/[...path]/route.ts   BFF 入口：AGENT_BACKEND 在这里分叉
│   │       └── lib/atomcode/                     ⭐ 适配层（M3）：daemon/events/history/live-hub
│   └── api/                 FastAPI（**源码一行没改**，部署时直接用公开 GHCR 镜像）
├── distro/                  ⭐ 发行版自己的东西
│   ├── workspace-template/  铺进工作区的一整套：.atomcode.md / .mcp.json / .hooks.json /
│   │   │                    .hooks/ / .atomcode/skills/ / holdings 等空目录
│   │   ├── .hooks/          五组 hook（guard / context / lang / audit / budget）
│   │   └── .atomcode/skills/ 6 个投研技能（由 tools/build_skills.py 从社区版 SKILL 转出）
│   ├── personas/            投研人设（fork 版才认 system_prompt_file，见 fork-patches.md）
│   └── mcp-tools.json       9 个 MCP 的工具清单快照（给前端做工具卡片用）
├── tools/                   9 个 MCP 的实现 + 技能转换器 + 评测/回归/hook 用例脚本
│   ├── akshare-mcp/ kronos-mcp/ truesource-mcp/   自研 MCP
│   ├── opencode-mcp/        6 个 hunter 系薄代理（反调 api 的 /api/internal/*）
│   ├── hooks/               hook 的可复现用例
│   ├── e2e/                 Playwright 端到端
│   └── eval/                A/B 评测与取证
├── deploy/                  ⭐ 部署
│   ├── install.sh           一键安装 / 升级 / 回滚
│   ├── up.sh                拉起（可重复执行）
│   ├── docker-compose.yml   六个服务
│   ├── Dockerfile.daemon    daemon 镜像：官方二进制 + 9 个 MCP 的 venv + 工作区模板
│   └── daemon/hca-init.py   容器启动时铺工作区、渲染 config.toml
├── db/migrations/           数据库迁移（0001–0022 与社区版镜像逐文件一致，0023 是我们加的）
├── pins.lock                AtomCode 版本与两道 sha256
└── docs/                    设计、实测、报告
```

关键取向：

* **daemon 里跑的是 AtomCode 官方二进制**，版本与 sha256 钉在 `pins.lock`，
  镜像构建时**双重校验**（npm 包的 tgz sha256 + 解出来的二进制 sha256），对不上就构建失败；
* 上层（web / api / MCP / 技能）尽量零改动，差异集中在 **BFF 适配层** 与 **distro/**；
* 数字一律实测。任何"看起来是数字"的东西都能回溯到一次真实调用（这是总控红线，不是风格）。

## 2. 四个外部面（改东西之前先想清楚放在哪一面）

| 面 | 能做什么 | 不能做什么 | 代码在哪 |
|---|---|---|---|
| **daemon HTTP/SSE API** | 起会话、发消息、收事件、切会话、查 MCP/技能状态、审批权限 | 按请求指定工作区（P0-2）；`/chat` 挂不上 MCP（P0-1） | `apps/web/app/lib/atomcode/`，端点手册 `docs/daemon-api.md` |
| **MCP（stdio）** | 加任何数据源/工具，自动出现在模型的工具清单里 | 控制模型**怎么用**工具 | `tools/*-mcp/`，注册在 `distro/workspace-template/.mcp.json` |
| **Hook（`.hooks.json`）** | 8 个事件：拦工具、改工具参数、改工具返回、往用户消息追加上下文、拦整轮、轮末记账 | 改助手正文（**没有这个事件**，见 `docs/hooks-design.md` §5）；改系统提示 | `distro/workspace-template/.hooks/` |
| **Skill** | 给模型一套可复用的工作流（目录式 `SKILL.md` + `references/`） | 让 `/技能名` 变成真的斜杠命令（P1-4：daemon 没有这个端点，只能当普通消息发） | `distro/workspace-template/.atomcode/skills/` |

决策树：
**要一份新数据 → MCP**；**要一条硬约束 → hook**；**要一套方法论 → skill**；
**要改界面行为 → BFF 适配层**；**想改内核 → 先证明上面四条都做不到**（M2 就是这么
用 A/B 评测把 fork 决策关掉的）。

## 4. 加一个 MCP

以"加一个 xxx 数据源"为例：

1. **写 server**：`tools/xxx-mcp/`，用 `mcp` 官方 python SDK。
   ⚠️ 6 个 hunter 系薄代理钉在 **mcp 1.x**（用 `@server.list_tools()` 装饰器，2.x 已移除），
   新写的建议直接用 2.x 并放进 `/opt/hca/venv`；两个 venv 的分工见 `Dockerfile.daemon`。
2. **拿不到数据要明确报错**，不许返回空壳或占位数字（总控红线 1）。
   参考 `tools/kronos-mcp`：没配 key 时**明确告诉你去哪申请**，不假装成功。
3. **控制返回体积**：超过 16 KB 会被 AtomCode 砍成"头 4 KB + 尾 4 KB"，
   **而且剩下的 JSON 语法是断的**，模型看不出少了什么就会拿记忆补
   （P0-11，`output_artifact.rs:79/82`，阈值写死、没有配置项）。
   **新写的 server 直接 `from hca_size_guard import fit`**（`tools/opencode-mcp/hca_size_guard.py`，
   与 6 个薄代理同目录、镜像里在 `/opt/hca/mcp/`）：超预算时裁成
   **合法 JSON + 一个 `_hca_size_guard` 块**，明说「共 M 条、这里只给了 N 条」。
   数据是 DataFrame 的话，参考 `akshare-mcp` 的做法——先限行数（`AKSHARE_MAX_ROWS`）
   再二分压字节（`AKSHARE_MAX_BYTES`），并提供列投影参数；**只限行数压不住宽表**。
4. **注册**：`distro/workspace-template/.mcp.json` 加一段。里面的 `${VAR}` 由 AtomCode
   自己展开（密钥不落盘）；`autoApprove` 必须配，否则用户每问一句都要点确认（P1-6）；
   `timeout_ms` 同时是 initialize 的超时，2 核机器上给到 120000。
5. **装依赖**：`Dockerfile.daemon` 的 `pydeps` 阶段。
6. **验**：`docker exec hca-daemon python3 /opt/hca/tools/dump_mcp_tools.py`
   能列出工具、`/mcp/status` 是 n/n connected，然后真问一句话看模型调不调。
7. **前端工具卡片**（可选）：`distro/mcp-tools.json` 加上工具名与展示信息。

## 5. 加一个技能

技能是目录：`distro/workspace-template/.atomcode/skills/<名>/SKILL.md`（+ `references/`）。

* 社区版的 SKILL 可以用 `tools/build_skills.py` 转（它会把 `needs_tools` 里的
  `uzi_stock_deep_analysis` 映射成 AtomCode 的 `mcp__uzi__stock_deep_analysis`，P0-4）；
* `SKILL.md` **正文写中文**。原 opencode 出过一次事故：英文 SKILL 让模型整段用英文回答
  （见 `docs/hooks-design.md` §5）；
* 引用的 `references/*.md` 必须真的存在（P1-14 就是引用了一个不存在的模板）；
* 验：`GET /skills` 数目对得上，然后真让模型用一次 —— 它会不会用、用得对不对，
  只有真问才知道。`docs/开发文档/M1-成果与测试报告.md` 有 6 个技能的验收记录。

## 6. 加一个 hook

完整版见 [`docs/hooks-design.md`](hooks-design.md)，这里只列最容易踩的四条：

1. `.hooks.json` 必须**严格 JSON**（不能有 `//` 注释），解析失败上游**静默忽略整个文件** ——
   表现是 `hooks list` 说文件找到了却 `(No hooks loaded)`；
2. hook 的 `command` **不做环境变量展开**，`${HCA_WORKSPACE}` 由 `hca-init.py` 替换；
3. 判定看 **stdout 最后一行 JSON**，所以纯文本注入的 hook 最后一行不能长得像 JSON；
   一律 `exit 0` + 用 stdout 表达语义（exit 2 的语义绕，见 hooks-design §3）；
4. 加了开关就要同时写进 `deploy/env.example` **和** `deploy/docker-compose.yml` 的
   daemon `environment` —— 只写一处容器里读不到。

## 7. 改 BFF 适配层

`apps/web/app/lib/atomcode/` 四个文件：

| 文件 | 职责 |
|---|---|
| `daemon.ts` | 连 daemon：读 token 文件、`daemonFetch`、开 `/live` 流、`/mcp/status` |
| `events.ts` | `TurnProjector`：把 AtomCode 的 SSE 事件投影成前端已有的 opencode 事件 |
| `history.ts` | 会话历史投影（刷新后恢复） |
| `live-hub.ts` | 单条上游 `/live` 流扇出给多个浏览器订阅者 + 断线重连 |
| `index.ts` | 路由分发：会话列表/新建/发消息/事件流/配置 |

两条铁律：

* **前端尽量零改动**（已拍板决策 1）。差异都塞进适配层；M3 全程只改了前端 1 处
  （工具名归一，防御性）。
* **切会话之后必须 `POST /mcp/reload` 并等到 `/mcp/status` 没有 `connecting`**（P0-10）。
  不补这两步，用户一点"历史对话"就悄悄失去全部数据源，而 `/mcp/status` 还显示 connected。

单测用的是**真实抓下来的 SSE 夹具**（`apps/web/tests/`），不是手写的假事件 ——
手写夹具只能证明代码跑通，证明不了它认得真实事件。

## 8. 跟上游 AtomCode 升级

```bash
# 1) 看上游有什么新版本（只读克隆在 ../atomcode-upstream）
cd ../atomcode-upstream && git fetch --tags && git tag --sort=-creatordate | head
# 2) **先出差异报告**（M5 加的，见下）
cd -; tools/upstream_diff.sh --to <新版本>
# 3) 改 pins.lock 与 Dockerfile.daemon 的三个 ARG（版本 / tgz sha256 / 二进制 sha256）
# 4) 重建并跑全套
bash deploy/up.sh --rebuild && bash tools/hooks/hooks-test.sh && bash tools/e2e/run.sh
```

### 8.1 `tools/upstream_diff.sh`（M5 加）

别直接 `git diff v5.1.0..v5.2.0` —— 上游一次发布动几万行，看不出**我们依赖的接口有没有变**。
这个脚本只比四个外部面，各抽成一份排序过的事实清单再 diff：

```
面 1  daemon HTTP 路由 + /live 的 SSE 事件（type 取值与载荷字段）
面 2  skill 解析（frontmatter 字段、目录约定、GET /skills 的回包形状）
面 3  hook（事件枚举、cc_name、.hooks.json 结构、输入输出 JSON 键）
面 4  MCP 配置（.mcp.json 字段、信任门、超时常量）
```

抽不到就写 `!! 抽取失败` 并让 `rc=3` —— **抽漏了报「无变化」是最危险的假阴性**
（升级方看到一片绿就换底座）。`tools/tests/test_upstream_diff.py` 里有 14 条测试钉这件事。

它还会：核对 npm 的 `dist.integrity` / `dist.shasum`、找出 `latest.json` 里该版本的
sha256 与 size、在目标版本的干净 worktree 上试打一遍 fork 补丁。

⚠️ **`latest.json` 的坑**：release tag 上那份写的是**上一版**（`v5.1.0` 的 tag 里
`version` 是 `v5.0.9`），同步 commit 落在打 tag 之后。照着 tag 读会锁错校验值。
脚本按文件内容回溯同步 commit，别自己另写一套读 tag 的。

实跑示例在 `docs/upstream-diff/`：5.0.9 → 5.1.0 只有一条新路由，
skill / hook / MCP 三面一处没变；5.0.8 → 5.0.9 则多了三条路由和一个
`McpConfigSource::Driver` 枚举值。

**但源码比对只能证明「接口没动」，证不了「行为没变」**（待办池 P2-15）。
差异报告第 4 节列了升级前必跑的 5 项冒烟，那些必须实跑。

### 8.2 契约清单

升级前**先读源码差异**，重点看这几处 —— 它们是本发行版依赖的契约，上游一改我们就会坏：

| 位置 | 我们依赖它的什么 |
|---|---|
| `atomcode-capabilities/src/cc_hooks.rs` | 8 个事件名、payload 字段、决策 JSON 的形状、`last_json_line`、exit 2 语义、BTreeMap 顺序 |
| `atomcode-capabilities/src/tools/mod.rs` | 工具清单（**新增工具就是新的绕过面** —— `bash_start` 就是这么被 M4 抓出来的） |
| `atomcode-capabilities/src/tools/output_artifact.rs` | 16 KB 截断阈值（P0-11）—— 我们的大小闸 `HCA_MCP_MAX_BYTES` / `AKSHARE_MAX_BYTES` 默认 15000 就是按它定的，阈值变了要同步 |
| `atomcode-capabilities/src/session/manager.rs` | `SessionMeta.turn_stats` 的字段（预算 hook 的 token 源） |
| `atomcode-coding/src/parts.rs` | `register_codeintel_tools` 门控、`with_transcript_path` |
| daemon 的 `/live*` 端点 | 整个 BFF 适配层 |

**每次升级都要重跑 `docs/regression-report.md` 那份清单**，尤其是「五组 hook」与
「全部 MCP」两节 —— 这两处对内核改动最敏感。

需要改内核才能过的情况，按计划 v0.2 §5.2 的补丁范围 fork：
`docs/fork-patches.md` 里有一份已经验证过四道上游 CI 门的最小补丁（M2 写好但**没有启用**，
因为 A/B 评测 89.6% ≥ 80% 的闸门）。

## 9. 已知的坑（会咬人的那几个）

按咬人程度排，完整列表在 [`docs/开发文档/待办池.md`](开发文档/待办池.md)：

| # | 坑 | 你会看到 | 怎么办 |
|---|---|---|---|
| P0-11 | MCP 返回超 16 KB 被砍成头尾各 4 KB，阈值写死 | 模型引用了一个工具返回里**搜不到**的数字 | MCP 侧压返回体积；`.atomcode.md` 里写死"看到 truncated 必须先 `fetch_output`" |
| P0-10 | 切会话后 MCP 工具全部消失，而 `/mcp/status` 仍 connected | 模型说自己没有 `mcp__*` 工具，改用 bash 抓数 | BFF 切会话后 `mcp/reload` + 等就绪（已做） |
| P0-1 | `/chat` 不挂 MCP | 工具调用返回 `unknown or unmounted tool` | 一律走 `/live` |
| P0-2 | `/live` 不能按请求指定工作区 | 多用户会共用一个工作区 | P0 只做单工作区；多工作区要多 daemon |
| P0-7 | `stop_reason=stopped` 区分不了"做完了"和"做一半" | 模型说"接下来我去查 X"然后流正常结束 | BFF 自己判完成度 |
| P0-9 | 模型用内置 bash 会弹权限，headless 不应答就死等 | 一轮挂住 300 秒 | `.mcp.json` 的 `autoApprove` 只管 MCP；bash 靠 guard 先拦掉 |
| P1-12 | `/live` 的 token 计量基本不可用（多数轮次 0） | 想统计成本却全是 0 | 用会话 `.meta` 的 `turn_stats`，或网关配额差值 |
| P1-16 | 8 个代码智能工具无条件挂载、关不掉 | 每轮固定 token 开销 | 能关的四类已关（省 3936 token/轮）；这 8 个要 fork 才能关 |

## 10. 提交约定

* 分支 `feat/<里程碑小写>`，测试通过后合并 `main`，**依次推 GitCode 与 GitHub**（禁止 `--force`）；
* conventional commits，中文正文，末尾带 `Co-Authored-By`；
* **改了行为就要有测试**，而且测试要能证明"改之前是坏的"——
  M4 的 guard 补漏是逐条对旧版复验过的（`docs/evidence/M4/guard-old-vs-new.txt`）；
* 报告里的每个数字都要能回溯到一次真实调用；拿不到就写 `—` 和原因。
